# AI 资讯开发文档

本目录放**只有人和评审读**的决策记录，定时任务运行时不读这里。运行时执行文件见 [../工程/README.md](../工程/README.md)。

## 文档索引

| 文件 | 作用 |
| --- | --- |
| [方案.md](方案.md) | **被批准规则的唯一权威正文**：产出体系、内容规则、数据源、榜单算法、运行架构、存储结构 |
| [版本规划.md](版本规划.md) | 版本路线、当前状态，以及「何时、为什么改」的迭代记录 |

| [提案/](提案/README.md) | 每轮开发方案与评审记录，一次评审一个文件 |

规则以 `方案.md` 为准，提案只记录「为什么这样改」；平台侧动作写进提案的「平台侧动作」并写明验收怎么查。

## 提案流程

1. 改流程、改规则、改数据源、改脚本契约、加产出类型 → 写提案；修文案、补注释 → 直接 PR；只改平台配置 → 记入 `版本规划.md`。
2. 状态流转：`草案 → 评审中 → 已批准 → 实施中 → 已完成`（或 `已放弃`）。**批准前不改代码**，实现后保留提案作为决策记录。
3. 每个提案末尾有评审记录表：日期、评审方、结论、对应提交 SHA。追加提交需复审时在 PR 评论 `@codex review`。
4. 门禁顺序：需求对齐 → 提案入库 + Draft PR → 方案评审 → 实现（代码 + 测试 + 验证结果）→ 代码评审 → 逐项回应 → 用户决定合并 → 运行验收。2026-11-12 起按 `协作契约.md` 2.1 的轻量一轮流程执行。

## 证据要求

每次提案与实现都要带：**问题证据**（命令输出、文件行号、失败记录、复现步骤）、**验证结果**（单测数量与结果、`check_portability.py` 结果、必要的端到端记录）、**评审记录**。没有证据的判断写成待验证，不写成结论。

## 维护约定

- **修改规则时先改 `方案.md`**，再同步执行手册、模板、脚本和配置，并在 `版本规划.md` 记录原因。
- 本目录与 `../工程/` 的改动都只能走 PR，评审后合并；周报、数据和状态文件由定时任务经 `coord.py` 直接推送 `main`，不需要人工确认。
- `提案/附件/2026-11-15-TEST_RUN-W45/` 是 2026-11-18 目录迁移**之前**的原始运行证据，其中的 `AI资讯/...` 路径字符串按原样保留，不代表当前目录结构；当前结构见 [方案.md](方案.md) 第 8 节。
- 定时任务的会话只用于运行和诊断，不承担开发；开发在开发会话里做。
