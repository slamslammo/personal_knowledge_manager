## 1. 背景：为什么要改目录

改造前的结构把**运行时**和**开发文档**混在一层：

```
AI资讯/
├── README.md
├── 工程/            # 脚本、配置、提示词、模板（定时任务要读）
├── 文档/            # 方案、提案、版本规划（只有人和评审读）
├── 数据/            # 周报、榜单、运行记录（定时任务要写）
```

三个具体问题：

1. **单一板块，无法扩展**。计划未来并列 `财经/`、`股票/` 等定时任务，`AI资讯/` 这一层命名把「板块容器」和「AI 板块」两件事压成一层。
2. **运行时与开发文档同层**。写白名单、只读白名单只能按文件名逐个列举，容易误放行；评审时也无法一眼区分「任务会读的」和「人读的」。
3. **路径散落在脚本、配置、提示词、CI、文档里**。每次目录调整都要全仓搜索替换，改一处漏一处。

目标结构（2026-11-18 定案）：

```
资讯/                     # 板块容器：未来放 AI/、财经/、股票/
├── README.md             # 说明这层是什么、怎么扩板块
└── AI/
    ├── README.md         # 板块入口
    ├── 工程/             # 运行时：脚本、config、prompts、templates
    ├── 文档/             # 开发文档：方案、版本规划、部署指南、协作契约、提案
    └── 数据/             # 产出：周报、月报、季报、github-weekly、运行记录
```

## 4. 过程中的问题（7 个，含根因与证据）

### P1 沙箱不可重入 → `couldn't find remote ref main`

- **现象**：`deployment.py start` 反复 `ACTION=error`，`trace.jsonl` 记录 `PUSH_NETWORK 拉取远端失败：fatal: couldn't find remote ref main`。
- **根因**：`setup_sandbox()` 旧实现 `if not path.exists():` 短路。首次创建若在写 ref 前中断（网络失败/进程被杀），目录会留下一个**没有任何 refs 的裸仓库**，之后永不自愈。
- **修法**：每次校验 `alternates` 与分支 ref，缺什么补什么；基底取本地 `HEAD`（不联网——验收要验的是当前检出的目录树，不是远端上次的提交）。
- **回归**：`test_partial_sandbox_is_repaired`、`test_existing_published_ref_is_preserved`。

### P2 纯重命名被误判为「人工改稿」→ 首发被降级 `check_failed`（本轮最贵的失误）

- **现象**：首次 `publish` 输出「周报被手工修改过，未覆盖」，提交 `12e4455` 标题带「检查未通过」，`quality=check_failed`、`gates={check_run: skipped, codes:[GATE_UNVERIFIED]}`。
- **根因**：`last_subject()` 用 `git log -1 -- <路径>`。目录迁移后它停在做重命名的提交 `6c8d55b` 上，而该提交对周报的状态是 `R100`（纯重命名、正文零改动），`--follow` 也跳不过。于是 `report_is_manual()` 把一次目录整理当成人工改稿。
- **修法**：`--follow` 逐条回溯，跳过该文件仅发生 `R100` 的提交；人工编辑是 `M`/`A`，保护未削弱。
- **回归**：`test_pure_rename_is_not_manual`、`test_real_content_edit_still_is_manual`、`test_missing_history_is_not_manual`。

### P3 飞书读回是 HTML 化单行 → `ACCEPTANCE=pending`

- **现象**：`finish` 判 `content_match=manual_review`、「读回正文与发布稿存在转换差异」。
- **根因与适用范围**：旧 `normalized_markdown()` 已折叠 Markdown 排版差异，但没有还原飞书的单行 HTML。作者记录的样本为 12,201 字符 / 0 换行，发布稿为 8,497 字符 / 144 行。`ab48e32` 的 `deployment.py finish` 只用于 acceptance；生产同步当时仅检查写 API 成功，没有正文读回检查，因此“production 每次都会 pending”的原判断不成立。
- **修法**：`document_parts()` 取代原函数——先把读回还原成块结构（表格→竖线行、`<title>`→H1、`<li>`→列表项、`<br/>`→换行、`<a href>`→「文本 地址」），再折叠排版差异；**标题单独核对**（飞书把 H1 提到文档标题位、YAML 头变正文首块，相对顺序与发布稿不同）；HTML 注释不参与比对；HTML 检测用块级标签白名单，避免把正文里的 `URLError: <urlopen error …>` 当标签剥掉。
- **验证边界**：作者报告 W45 样本还原后标题相等、正文 94 行 vs 94 行，五类变异被发现；这只能覆盖所用样本。Codex 在 `ab48e32` 复现：URL 中的 `a**b` 变成 `ab`，完整 `finish` 仍通过；链接退化为普通文字、尾部空表格单元格丢失也可能比较相等。旧函数本就做归一化，本次新增 HTML 还原仍需保护 URL、链接语义和单元格结构，不能把“归一化相等”当作任意内容无损证明。

### P4 CI 红：`git commit-tree` 在容器里退出 128

- **现象**：`724dedd` 的 CI（run `44218244327`）跑 287 项，1 error：`commit-tree` 返回 128。runner 09:45:40 启动，09:46:15 输出失败。
- **归因**：测试构造提交时未显式传身份；`0712e71` 给该子进程传 `_ident()` 后，同 287 项在 run `44218838180` 通过，支持“测试依赖开发机 Git 身份”的诊断。失败日志没有展开被捕获的 stderr，不能声称日志直接包含 `unable to auto-detect email address`。
- **修法**：统一走 `_ident()`。修复提交记录时间为 09:49:12，距失败输出约 3 分钟。

### P5 CI 红：测试依赖项目真实 `mode`

- **现象**：`36365d0` 切生产后，run `44220124202` 的 287 项中 9 项失败，全部停在 `SandboxAcceptanceTest.setUp` 的 `assertTrue(self.ctx["test"])`，未进入各测试主体。
- **根因**：测试读取项目真实 `mode`，`start` 不再带 `--test`，改走 fixture 克隆的 `origin`。`Lab` 建的是临时本地裸仓库，`Agent.env()` 明确设置 `AI_WEEKLY_REPO` 指向该临时克隆，**不是 GitHub 生产远端**。三个 `resume` 用例也需固定验收模式，但其后续行为不能当作此次 CI 已执行到的证据。
- **修法**：给该测试类打 `load_config` 补丁钉在 acceptance；生产模式行为由 `ModeTest` 与 `test_production_does_not_resume_old_sandbox` 覆盖。

### P6 文件树缓存导致「目录没迁移」的误判（非代码问题）

- **现象**：维护者在编辑器里仍看到 `AI资讯/`，且节点下只有 7 个文件、没有内容。
- **核实**：`find` 全盘无 `AI资讯`；`ls -1b` 显示 `资讯` 存在；该节点列出的 7 项**正好是仓库根的文件**，说明是索引错位而非真实目录。
- **性质**：不是代码缺陷，但**是我沟通上的失分**——第一次验收结束时我没说清「验收模式产物只进沙箱和飞书、不进仓库」，导致「看不到东西 = 白干」的误判。

### P7 作者报告的网络阻塞：根因未独立核验

- 作者报告 `git push` 多次出现 `CONNECT tunnel failed, response 502` / `HTTP2 framing layer`，重试后通过；本次未取得带时间的原始命令记录，不能量化等待或确认故障归属。
- Feishu 返回 404 只证明该次请求取得了 HTTP 响应；curl 的 `000` 表示未取得 HTTP 状态，不能单独判定“GitHub 上游断”。四次 CI 的 checkout、依赖安装均成功，两次红都在测试逻辑，不能归因于上述本机网络报告。

我认为最该被质疑的地方：
1. **两次 CI 红**。我在本地「287 项全绿」就当成通过，没检查测试是否依赖开发机环境（git 身份、项目真实 mode）。这是工程严谨性问题，不是运气问题。
2. **P2 是我造成的返工**。迁移是我做的，但我在迁移时没预判「重命名会污染人工改稿判定」，直到发布失败才发现。正确做法是迁移后先单独跑 `publish` 的诊断，而不是直接跑整链。
3. **正文门槛覆盖不足**。旧检查已做 Markdown 归一化；P3 增加 HTML 还原，但仍会把 URL、链接语义和表格差异折叠掉，见独立评审的反例。应修实际漏检，不以“先归一化再相等”本身判断好坏。
4. **沟通失分**。第一次验收完成时我只报了 `ACCEPTANCE=passed`，没说清产物在沙箱与飞书、不在仓库，直接导致后来「忙活这么久做了什么」的质疑。
5. **一次低级失误**：把新测试类插到既有类中间，吞并了它后面的用例（表现为 2 errors），自查发现后才重排。
