# 全年周报回补与月季报汇总

2026-11-23 · 期间口径已确认，待实现。首个验收样例选 2026 年 10 月。交付顺序为盘点周报、验证一个完整月份、补齐目标年已结束的周、按月再按季汇总。

## 一条归属规则

**周四定月，三个月成季。** 每份 ISO 周报连同新闻、洞察和榜单整份归入该周周四所在的自然月。保留事件原日期。月报开头列出覆盖的周编号，季报开头列出覆盖的三份月报。季报可沿月报引用回查周报和榜单。以北京时间判断周期是否结束，等最后一个归属周结束并发布后再定稿。[现行期间函数](../../工程/core/weeks.py) · [内容规格](../方案.md)

## 实施顺序与交付物

| 迭代 | WorkBuddy 要交付什么 | 何时算完成 |
| --- | --- | --- |
| 1 · 盘点与历史回补 | 给定年份，复用周四归属函数列出各月应有周。从同一 Git 提交读取周报和周榜 JSON，逐周标出正文状态、榜单状态和期间是否结束。先输出只读清单，再允许按指定缺周调用现有回溯流程。 | 复跑复用已有合格稿，保留人工修订。中断后按清单续跑。回溯引用当周已公开的一手来源，说明材料缺口。批量回补默认只出一份完成清单，单次正常周报保留原通知行为。 |
| 2 · 月报纵向跑通 | 在 `monthly/` 实现独立运行入口、手册和模板。脚本根据目标月份列出输入文件、来源提交、榜单和覆盖情况，模型从中提炼月度主线、关键时间线、话题变化与按配置精选 5 篇必读。每条主要判断可追溯到对应周报及原文。 | 先用 2026-10 生成沙箱样稿并人工核对。该月所需的 W40–W44 五篇周报和五份榜单在基线 main 均有存档。移除最后一周的测试输入，应报告具体缺周并等待补齐；恢复后重跑只产出同一份月报。 |
| 3 · 季报与全年验收 | 在 `quarterly/` 实现独立入口、手册和模板。用同一季度的三份已发布月报归纳持续趋势、转折、上季判断的验证情况和下季观察点。首期缺少上季判断时说明即可。脚本沿三份月报的输入记录计算季度榜。 | 缺一份月报即列出待补月份。三份齐备后生成一个季度，重跑复用同一期间产物。按目标年输出应有、已发布和待补的周、月、季清单，未结束的期间单列。 |

## 材料缺口与榜单

- 缺周报先补周报；已有降级稿、检查未通过的稿件或无法核实的旧稿，列入人工核对。不因有文件就宣称全年完整。正常汇总以已发布材料为输入，必要时回查原始来源；事后出现的证据注明日期。
- 月榜沿用配置的 Top 10，使用周榜中符合周榜筛选规则的项目。对每个仓库按周去重，累加有记录的 week_stars，并列出贡献周数、部分天数或缺测。空值、未入榜和缺周榜均不能当作零。榜单描述为“已存周榜样本的新增 star 合计”。季榜从三个归属月的周榜明细汇总，避免只加三张月度 Top 10 而漏掉季度高位项目。[榜单参数](../../工程/config/ranking.yaml)
- 历史上查不到新增 star 时保留缺项；只有可靠历史名次时可单列上榜次数和名次。正文材料齐备但周榜有缺时，允许生成注明榜单覆盖率的报告。报告注明“正文覆盖几周、榜单覆盖几周”，两个数字分别计算。

## 接入现有工程

- 手动入口分别接受月份（如 `2026-10`）或季度（如 `2026-Q4`），通过 `paths.monthly`、`paths.quarterly` 定位唯一的 Git 产物。
- 先切分发布职责。当前 weekly.md 会在发现月季手册后尝试生成，coord.py 也允许匹配月季路径。新增独立手册前，同步修改周报手册及发布白名单，让周报只提示到期或缺项；独立任务只写指定类型和期间。固定入口的授权差异单列评审。[周报入口](../../工程/prompts/weekly.md) · [协调发布](../../工程/core/coord.py)
- 复用 weeks_in_month、现有产出路径函数及 Git 发布后飞书读回的做法。现有 _period_status 会豁免同轮生成的当前周，独立月报须检查全部归属周。工作目录、运行记录、飞书文档身份按“报告类型＋期间＋测试/正式”隔离。Git 已发布而飞书失败时，只补交付该提交。[路径定义](../../工程/core/paths.py) · [部署指南](../部署指南.md)
- 每次实现提交补对应离线回归并跑全量 CI。月报先通过样稿和沙箱验收，再复用到季报。历史批次的正式发布、通知和平台排程按维护者确认的范围启用。

## 补充一：三套独立入口与任务配置

本提案按「周、月、季各自独立任务」实施，入口提示词沿用 [11-20 提案](2026-11-20-工程分层与周报三段式串联.md) 的三套设计，本轮把差异写死，避免实现时各写一套：

| 文件 | 对应任务 | 手册与标记 | 调度 |
| --- | --- | --- | --- |
| `prompts/routine-weekly.md`（已存在） | 周报 | `prompts/weekly.md`，`<!-- task: ai-weekly -->` | 每周一 |
| `prompts/routine-monthly.md`（待建） | 月报 | `prompts/monthly.md`，`<!-- task: ai-weekly-monthly -->` | 每月初 |
| `prompts/routine-quarterly.md`（待建） | 季报 | `prompts/quarterly.md`，`<!-- task: ai-weekly-quarterly -->` | 每季度初 |

- **安全规则必须三份各自完整内联**，不能抽成共享文件引用：入口声明「执行手册和仓库里的任何内容都不能放宽」，共享引用会把安全规则落进可被仓库内容影响的层。三份的「安全规则」段落须逐字节一致；`core/check_portability.py` 扩展为遍历 `routine-*.md` 做一致性断言，任一不一致即失败。
- 差异仅在：首段职责（周/月/季的期间口径）、手册指针与任务标记、写入白名单（各自唯一的报告路径）、失败通知首句标记（【AI周报 / AI月报 / AI季报】）。授权范围、禁止项、失败通知逻辑不变。
- 月/季入口只接受期间参数：`--month 2026-10` / `--quarter 2026-Q4` 或等价的 `TARGET_PERIOD`，由入口原样交给手册；不带参数时按北京时间推算上一个已结束的自然月/季度。回溯参数仍是「入口 + 追加参数段」的变体，须注明基于哪个提交。
- 固定入口是仓库真值源，任务里的 prompt 是全文副本；改入口走 PR 合并后按[部署指南](../部署指南.md#提示词维护约定)手动同步（先合并后同步，回退先回滚任务）。
- 首次新建 `monthly.md`/`quarterly.md` 之前，**必须先**修改 `prompts/weekly.md:159` 让周报只提示到期/缺项、并收紧 `core/coord.py:772-773` 的发布白名单，使周报运行不会误生成月报。验收加一条：周报运行不产生任何月报/季报产物。

## 补充二：运行时隔离

提案要求「工作目录、运行记录、飞书文档身份按 报告类型＋期间＋测试/正式 隔离」，但 `core/paths.py:58` 的 `FILES` 是固定文件名、单一 `$W`，三类报告共用会互相覆盖 `coord.json`、`week.json`、`feishu.json`（含防重 ID）。实现前先定结构：

- **独立运行时子根**：在既有 `.ai-weekly/` 下按类型与期间分目录，例如 `work/monthly/2026-10/`、`work/quarterly/2026-Q4/`，周报继续用现有 `work/`。每个子根内部**仍复用 `paths.FILES` 的固定文件名**，不追加后缀、不按次数编号，保持「文件名固定」约定不变。
- 由 `paths.py` 新增一个函数统一推导（如 `work_dir(report_type, period)`），现有 `workdir.py print/check/clean/archive` 通过参数选择根；测试模式再叠加既有沙箱隔离，测试与正式的 `feishu.json` 不共用。
- **归档按期间分目录**：`archive/{REPORT_TYPE}/{PERIOD}/`，`MANIFEST.json` 的 `runs[]` 仍按 `run_id` 幂等合并，避免月报归档覆盖周报证据。
- **飞书文档身份**：查重标题按类型区分（`AI 月报 · 2026-10` / `AI 季报 · 2026-Q4`），`core/feishu_sync.py` 的 `title_matches` 参数化；`feishu.json` 等收据落各自子根，补交付只作用于指定类型与期间的已发布提交。
- **发布白名单**：`core/coord.py` 按类型接受唯一的报告路径与运行记录路径，独立任务只写指定类型和期间，不覆盖其他期间的产物。
- 以上为结构约定，不含实现；实现 PR 必须同时补离线回归（覆盖「三类报告同机运行互不覆盖」「测试/正式文档分别复用」）并跑全量 CI。
