# AI 资讯任务协作契约

本文件规定开发、评审、合并与运行的边界。内容规则见 [方案.md](方案.md)，当前平台与运行安排见 [部署指南.md](部署指南.md)，变更缘由见 [版本规划.md](版本规划.md)。

## 1. 写入与决策边界

| 内容 / 决策 | 负责方式 |
| --- | --- |
| `资讯/AI/工程/`、`资讯/AI/文档/`、板块 README | 开发会话修改，走 PR，评审后由用户合并或明确授权合并；不直接推 main |
| 当期周报、榜单数据、运行记录及到期月报/季报 | 运行会话按入口授权，经 `coord.py` 直接推 main，无需逐次确认 |
| 状态文件 | 只由 `coord.py` 写；人工修复须走 PR 并说明原因 |
| 上线、平台切换、调度启停、模型档位、仓库挂载 | 用户决定；仓库修改不能替代平台操作 |

WorkBuddy 负责调查、实现、自测与处理评审意见；Codex 的独立评审阶段只读，不代替用户做取舍。运行会话只运行和诊断，工程修复回开发流程。生产输出直接推送的授权不适用于工程和文档修改。

## 2. 变更入口

| 变更 | 最小流程 |
| --- | --- |
| 流程、内容规则、数据源、脚本契约、产出类型，或验收/失败语义有实质变化 | 提案入库并开 Draft PR；用户确认取舍后实现，代码与提案放同一 PR |
| 已批准范围内的缺陷修复，或文案、注释、链接修正 | 直接小 PR，说明问题、改动与验证；不另造提案或重复审批 |
| 仅平台配置 | 用户操作；当前安排更新部署指南，变更原因记版本规划 |

方案评审不等于实现评审。实现中发现范围或规则要变，先在原提案说明并确认取舍；已批准的修复按原授权继续。

### 2.1 一轮评审与收口

1. **实现与自检**：先用小型离线样本验证具体问题，再检查同类位置和必要参数组合；不靠反复采集、重写整周定位工程问题。
2. **集中评审**：PR 准备好后转 Ready for review。评审绑定提交 SHA，只提影响功能、内容可信度或正常发布的问题；开发方按“具体问题 → 共同根因 → 同类位置”一并修复。
3. **验证最终版本**：工程、配置或 CI 工作流改动须完成相关回归，并以**最终 PR head SHA 对应的 CI**完成一次全量测试。追加提交后旧结果不代替新版本。当前 `ai-weekly-tests.yml` 只自动检查 `资讯/AI/工程/**` 和工作流自身；纯文档 PR 未触及这些路径时不自动运行 CI，做一致性、链接与 `git diff --check` 检查，不能把“无运行”记成“CI 通过”。
4. **合并**：用户执行或明确授权。PR 写清本轮已落地、未落地、验证版本与结果。一般风格和低概率边界进待办；仅有明确关键缺陷或测试失败时，对该问题追加核验，不自动展开下一轮全面审查。
5. **必要运行验收**：合并后按授权运行一次；纯文档修订不触发周报。交付缺项先从已发布 SHA 补交付或只读核对，不重跑整周。当前平台安排以部署指南为准，不因修文档启用调度。

Git 提交/质量门、飞书正文读回、通知 API 结果与实际收件分别留证；API 成功不等于已收到或已读。证据缺失写 pending，不合并成“全部完成”。复现输出、测试结果和评审结论必须绑定版本；有提案则记入其评审表，小 PR 记在 PR 描述中。

## 3. PR 审查与验证

- GitHub 审查只能读取已入库内容；重要决策不能只留在聊天里。
- 追加提交不保证自动复审；确需复审时在 PR 评论 `@codex review`。`Completed` 只表示执行结束，不代表无问题，也不证明分支已配置强制审查规则。
- 报告只写代码或运行证据支持的结论；缺项与未验证项单列。参数组合检查同类缺陷，避免为消除单个反例连续增加例外入口。
- Python 依赖写进 `requirements.txt`；本地与 CI 使用同一份依赖。平台侧动作单列并说明如何核验。
