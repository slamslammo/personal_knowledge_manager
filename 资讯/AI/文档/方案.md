## 1. 目标与范围

周报记录一周发生了什么，月报归纳哪些变化正在持续，季报检验跨月趋势和上季判断。正式全文保存在 GitHub `main` 的[数据目录](../数据/)。读者也可通过飞书年度表按时间浏览摘要、打开原稿。

| 历史专题 | 缺少周报存档的期间，回查当时的原文与带日期的讨论记录 | [历史月报示例](../数据/月报/2026/2026-08.md) · [对应季报](../数据/季报/2026/2026-Q3.md) |

## 2. 产出体系与时间规则

### 2.1 周的定义

通常汇总运行日所在周的上一周。以北京时间周一 00:00 至下周一 00:00 前为一周，使用 ISO 周年与周号。例如 2026-12-28 至 2027-01-03 为 `2026-W53`。回溯可指定已结束的报告周。

### 2.2 月份与季度的归属

整份周报归入其周四所在的自然月，连续三个自然月组成一季。例：2026-W40（9/28–10/4）的周四在 10 月，归入 10 月和 Q4。2026 年 10 月含 W40–W44 五周。新闻保留实际发生日期，跨期引用同一事件时标明已有事实和新进展。

### 2.3 生成时机与到期判定

相邻两周的周四跨月或跨季时，对应周期到期。周报任务只提示到期与缺项。月报、季报由各自入口运行，在最后一个归属周结束后读取同一 Git 提交的输入。缺归属周的周报时月报暂缓，缺三个月中的任一正式月报时季报暂缓。缺榜单则记录缺测。[日期规则](../工程/core/weeks.py) · [期间准备与发布](../工程/core/period_report.py)

## 3. 周报

标题采用 `AI 周报 · {WEEK}（{M/D}–{M/D}）`，回溯版加「（回溯版）」。正文按 ①、洞察、②、③、④、⑤、数据说明排列。[周报模板](../工程/templates/weekly.md)

### 3.1 元数据

`week`、`range` 与报告周一致。`topics` 选 3–6 个受控词，`orgs` 参照同一词表的 `org_names`，`repos` 取 GitHub 榜单 Top 5。降级稿写 `quality: degraded`。[受控词表](../工程/config/topics.yaml)

### 3.2 板块归属优先级

同一事件按 **② > ③ > ④ > ⑤** 选择详写位置。③ 遇到已在 ② 详写的项目仍保留排名、项目名与数字，标「详见 ②」。厂商公告归 ② 或 ③，可附 HN 热度。个人实验、技术博客和评论可入 ④。⑤ 和洞察可引用前述条目。

### 3.3 ① 本周概览

选 3–5 项最重要的变化，每项用一个粗体短标签和一句话说明。

### 3.4 ② 新发布与技术 Top 5

最多 5 条。覆盖重要模型、产品、API、新技术或论文，每项说明变化及受影响的人。发布类附具体官方原文，新概念须有官方技术报告或至少两个独立来源。HN 讨论能追到一手原文时并列两者，仅有媒体报道时注明来源。

### 3.5 ③ GitHub AI 项目热度 Top 5

名次、项目链接、总 star 和周增量取自脚本，开头注明 UTC 口径。说明用途、走红原因、相关文章或视频、适用人群与风险；找不到传播材料时如实说明。候选、新晋、HN 热议和排除项目保存在榜单数据。

### 3.6 ④ 传播文章 Top 5

从报告周内达到配置分数线的 HN AI 相关文章或讨论中选取。同一原文仅保留最高分帖子，按分数、评论数降序排前 5。判重忽略协议、www、末尾斜杠、utm 参数和锚点。表格给排名、原文链接、摘要、传播原因、分数、评论数和 HN 链接。无原文的帖子链接到 HN，原文不可读时标「原文未能读取」并说明依据。[榜单配置](../工程/config/ranking.yaml)

### 3.7 ⑤ 热点话题 Top 5

从发布、HN 讨论和搜索结果归纳 5 个话题，写起因、进展与争议，各附 2–3 个代表链接。④、⑤ 表格每格一两句话，单元格长度按榜单配置检查。

### 3.8 洞察

从 ②–⑤ 提炼 2–3 个判断，每条写结论、支撑它的周报条目、1–2 篇原始材料及阅读价值。

### 3.9 数据说明

脚本从本轮记录填入来源状态、覆盖、跳过项和搜索次数；模型补充降级与缺失、AI 相关性改判原因和可疑内容的来源链接。[整理脚本](../工程/weekly/finalize.py)

### 3.10 通用写作规则

事实与链接均须有采集或搜索依据。仅有媒体报道、日期待核实、数字来自转述时分别说明。降级稿保留榜单数字、文章候选与数据说明，未完成的正文标「本期降级，未生成」，元数据与通知标明降级。

## 4. 月报

以全部归属周的已发布周报为正文依据，结合每周榜单和可得的运行质量记录。先概括月度主线，再按事件原日期整理关键时间线，说明话题的新增、延续与消退，从周报洞察中选 5 篇必读并说明理由。每个判断指向具体周报或原文。[月报模板](../工程/templates/monthly.md)

月度 GitHub Top 10 按仓库汇总已存周榜明细里的 `week_stars`，保留贡献周数和覆盖天数。包括符合条件但当周未进 Top 5 的项目。空值、缺榜与未入样本各有不同含义，均不能作零。正文与榜单分别标覆盖周数。[聚合算法](../工程/core/period_aggregate.py)

## 5. 季报

以三份正式月报为正文依据，围绕跨月才看得到的变化组织季度主线、技术方向和产业趋势。逐条回看上季判断，区分当时能知道的事与事后证据，再给出下季可验证的观察点。首期缺少上季判断时明示。季度 GitHub 榜从全季归属周的榜单明细重算，避免拼接三个 Top 10 时遗漏长期累计靠前的项目。[季报模板](../工程/templates/quarterly.md)

## 6. 数据源与 GitHub 榜单

### 6.1 采集信息源

Trendshift 提供周榜和增量，OSS Insight 补充仓库资料，HN Algolia 提供本周讨论，Hugging Face 提供论文候选。来源缺失记录在数据说明。

### 6.2 搜索信息源

优先使用官方公告、论文、代码仓库和监管原件。英文科技媒体、个人技术博客、HN 和 YouTube 补充背景与传播证据。中文媒体和 Newsletter 不纳入取材。[来源配置](../工程/config/sources.yaml)

### 6.3 GitHub 热度榜算法

1. **选候选。** 取当周 Trendshift 周榜约 25 项。榜外项目只能作为 HN 热议补充。周榜未就绪时先做其他板块，再按配置重试。
2. **判定 AI 相关性。** 覆盖大模型、智能体、训练推理、RAG、MCP、AI 编程或多模态生成等，拿不准时保留。沿用有依据的往期判定，改判须说明。手工排除合集、纯链接和越狱提示词合集；归档、fork、仓库不存在及疑似刷星按当周复核。
3. **计算增量。** 求仓库对应 7 个 UTC 日期的每日新增 star、fork 之和，比北京时间周界晚 8 小时。记录覆盖天数，全缺时留空。OSS Insight 优先补查增量靠前、新晋候选、HN 热议和递补项目。疑似刷星须同时满足低新增 fork/star 比率和少量未关闭 issue，补查失败记未核查。
4. **排名、归档。** 按新增 star 降序，缺值置后。同分再看新增 fork 和 Trendshift 名次。新晋项目按截至报告周周日的创建天数，从当周 Top 5 之外的候选中按同一规则选取。HN 热议项目须满足配置分数线且未列入 Trendshift 周榜。保存全部候选、排除原因和补充项目。Trendshift 仓库页的每日数据约覆盖 61 天，回溯优先取当周存档。

阈值和数量取自配置，具体计算与数据校验各有独立入口。[榜单配置](../工程/config/ranking.yaml) · [排名脚本](../工程/weekly/rank_github.py) · [数据校验](../工程/core/validate.py)

## 7. 质量门槛

- **周报。** 检查结构、链接、榜单、采集证据和搜索次数。通过记 `full`。降级稿记 `degraded`，免搜索下限、仍受上限约束。返工用尽后，结构或运行证据不完整、检查无结果时停止；其余允许发布的未通过项记 `check_failed`，在提交说明和通知标明。保留远端人工改稿时记 `GATE_UNVERIFIED`。回溯质量覆盖只允许豁免材料时间早于本次运行。[周报检查](../工程/weekly/check_run.py) · [质量推导](../工程/core/quality.py) · [运行参数](../工程/config/runtime.yaml)
- **正式月季报。** 准备时固定来源提交，发布前复核输入是否变化，核对正文所属期间、必需板块、主线、榜单与来源。来源更新后须重新核稿。输入报告降级、周报发布质量有已知问题或归属周榜单有缺时，标 `degraded` 并记录覆盖。相同正文重跑复用已有提交，已有不同正式稿走修订 PR。[发布实现](../工程/core/period_report.py)

## 8. 2026 年 Q1–Q3 历史专题

当时没有可复核的正式周报与周榜存档。按自然月整理当期原文和带日期的 HN 讨论，再从三份专题月报提炼季度变化。保留原文或投稿的日期含义，标明 `quality: 专题回顾` 与正文、榜单各 0 周；这里的 0 表示正式周报覆盖数。

A 级事实给出可回查来源，B 级归纳列出支持材料、局限及仍待核对的判断。缺少直接依据的推测不量化。HN 分数只说明该帖讨论热度；历史专题不据此重建 star 增量、排名或周报。9 份专题月报与 3 份专题季报可从数据目录按期间查阅。[历史月报](../数据/月报/2026/) · [历史季报](../数据/季报/2026/)

## 9. 飞书年度视图与通知

### 9.1 全文源与年报视图的分工

**GitHub `main` 是唯一全文真值源**：报告全文、榜单与运行记录都在 Git，修订只走 PR。飞书不做全文副本——年度表是按时间浏览的摘要索引，bot 通知只负责送达。早期用飞书 docx 分发全文的做法已废弃（[旧版设计](提案/2026-11-14-飞书接入与定时任务收敛.md)）。年度表每行只存期间、层级、覆盖情况、3 条核心事实和 GitHub 正文链接；读者从表中定位期间，点开正文链接读全文，或从通知里的记录直达链接回到年度表当期行。[展示设计与取舍](提案/2026-11-24-年度资讯档案展示规范与历史专题.md)

### 9.2 年度表设计

- **三级时间层级**：`归属年 → 归属季 → 归属月`。季报汇总行放在 `00 · 季度汇总`，月报与各周按排序键排在对应月组；周报按周四所在自然月归属（见 2.2）。
- **每期一行**：`published_row()` 从已发布提交的正文提取「本周概览 / 月度主线 / 季度主线」要点，写 3 条核心事实并**逐行显示**；不写「本地草稿 / 未提交 / 覆盖 0 周 / 待生成」等运行元信息。正式行读已发布提交，历史专题保留其证据口径。
- **报告链接可点击**：字段是 `type: text` + `style.type: url`，不是独立字段类型。写入按 lark-cli 的 CellValue 约定传裸 URL；`+record-list` 读回会渲染成 `[显示文本](链接)`，比较前用 `normalize_link()` 归一，避免把 CLI 表现层差异误判成索引未更新，也避免错误链接被放过（[锁定的用例](../工程/tests/test_annual_index.py)）。
- **记录直达链接**：更新索引后用只读命令 `+record-share-link-create` 取当期记录的分享链接，写入运行时收据 `annual-index.json`（含 `period`、`sha`、`record_id`、`url`）。周报、月报、季报共用同一路径契约 `record_receipt_path()`；通知按 `period + sha` 校验后才使用，取不到就不写链接、不伪造、也不回退 GitHub 全文链接。收据在 `CLEAN_PRESERVE` 中，清理运行时目录不会丢。
- **索引读回核对**：以用户身份更新同一期间行并读回，字段或链接不一致会重写。索引或通知未确认时保留已发布提交，按缺项补交付。[索引脚本](../工程/core/annual_index.py)

### 9.3 通知设计

正式运行顺序固定为 **Git 发布 → 年度表索引 → bot 通知**（[月季报发布](../工程/core/period_report.py) · [周报交付](../工程/weekly/deliver.py)）。三条链路共用同一套飞书 Markdown 通知格式（`feishu_sync.py notify` 固定用 `--markdown`）：

- **标题**只留栏目与期间：`【AI 周报 W47】` / `【AI 月报 2026-10】` / `【AI 季报 2026-Q4】`，单独成行，后面不接摘要或总结；异常时追加 `｜失败`、`｜降级` 等标记。
- **小节标题加粗**（如 `**月度主线**`），要点用 `1）`、`2）`、`3）` 逐行列出；**核心结论与关键内容用成对 `**` 加粗**，飞书里显示为深色粗体，便于快速定位重点。
- **不重复暴露链接**：原文 URL 已收录在 Git 正文，GitHub 正文链接留在年度表当期行供检索；通知里都不贴，只在尾部给 `年报：<年度表当期记录直达链接>`。
- **发送判据**：`NOTIFY=sent` 与收据里的 `status=api_accepted`、`message_id` 即视为发送成功。脚本不查询送达或已读，不把「接收人确认」列为缺项；只有结果未知（`NOTIFY=unknown`）或发送前确定性失败（缺 CLI / 接收人配置）才按补交付规则处理，未知时先核对消息实体避免重复发送。
- **沙箱**跳过飞书写入与发送，只保留本地提交、正文与通知预览。

W47 的通知按旧格式发出且不重发，新格式从下一期（W48 及之后的月报、季报）生效。未来跨年度的 HTML 深度年报另见[版本规划](版本规划.md)。[部署与排障](部署指南.md)
