# AI 周报规格

完整结构见[周报模板](../工程/templates/weekly.md)，运行步骤见[执行手册](../工程/prompts/weekly.md)。

## 1. 目标与范围

周报汇总上一周的 AI 关键内容，保留原始链接，供以后检索和比较。月报、季报用于对已有周报做阶段性分析。

## 2. 产出体系与时间规则

### 2.1 周的定义

通常汇总运行日所在周的上一周。每周从北京时间周一 00:00 开始，到下周一 00:00 前结束，使用 ISO 周编号。跨年也用 ISO 周年，例如 2026-12-28 至 2027-01-03 为 `2026-W53`。回溯可指定报告周，当前运行安排见[部署指南](部署指南.md)。

### 2.2 月份与季度的归属

一周归入其周四所在的月份和季度。例如 2026-W40（9/28–10/4）的周四在 10 月，归入 10 月和 Q4。

### 2.3 生成时机与到期判定

[weeks.py](../工程/scripts/weeks.py) 已实现到期与补生成判定。报告周与下一周的周四跨月或跨季时，相应月报或季报到期。未到期时检查最近一个已结束的对应周期。缺少该期报告且包含的周报已齐备时可补生成。到期但相应周报缺失时，在当期周报的数据说明里注明。

月报和季报的任务手册、模板仍待实现。当前执行到到期分支时，按执行手册记录原因并跳过。

## 3. 周报

标题采用 `AI 周报 · {WEEK}（{M/D}–{M/D}）`，回溯版在标题末尾加「（回溯版）」。正文按 ①、洞察、②、③、④、⑤、数据说明排列。

### 3.1 元数据

`week`、`range` 与报告周一致，`topics` 从[受控词表](../工程/config/topics.yaml)选 3–6 个，`orgs` 参照同一词表的 `org_names`，`repos` 取 GitHub 榜单 Top 5。只有降级版写 `quality: degraded`。

### 3.2 板块归属优先级

同一事件按 **② > ③ > ④ > ⑤** 归属，只在优先级最高的板块详写。③ 中已在 ② 详写的项目保留排名、项目名称和数字，标注「详见 ②」。厂商或项目方的产品、模型、版本、开源仓库发布公告归 ② 或 ③，HN 热度随对应条目写。个人实验、技术博客、评论与分析可以进入 ④。⑤ 和洞察可引用其他板块。

### 3.3 ① 本周概览

3–5 条最重要的变化，每条一句话，开头用简短的粗体标签。

### 3.4 ② 新发布与技术 Top 5

最多 5 条，选重大发布、重要产品与 API、新技术或新概念、有影响力的论文或技术报告。写清是什么、新在哪里、对谁有影响。发布类附具体官方原文，新概念须有官方技术报告或至少两个独立来源。引用的 HN 帖子有官方或其他一手原文时，附该原文和 HN 讨论链接。仅有媒体报道的材料要标明来源。

### 3.5 ③ GitHub AI 项目热度 Top 5

名次、项目链接、总 star 和本周新增 star 以榜单脚本的输出为准。每项说清项目用途、本周走红的原因、相关文章或 YouTube 视频讨论了什么，以及适用人群、成熟度和风险。找不到传播材料就如实说明。候选、新晋、HN 热议和排除项目留在数据文件，正文只展示 Top 5。榜单开头注明 UTC 数据口径。

### 3.6 ④ 传播文章 Top 5

只选报告周内达到[榜单配置](../工程/config/ranking.yaml)分数线的 HN AI 相关文章或讨论。同一原文只留分数最高的帖子，按分数降序，同分按评论数降序，取前 5。判断同一原文时忽略协议、www、末尾斜杠、utm 参数和锚点。表格含排名、标题与原文链接、摘要、传播原因、分数、评论数和 HN 讨论链接。链接和数字以采集数据为准。Ask HN 等无原文的帖子，标题链接用 HN 讨论链接。原文不可读时，可根据 HN 讨论和搜索结果写摘要，并注明「原文未能读取」。

### 3.7 ⑤ 热点话题 Top 5

从本周发布、HN 讨论和搜索结果归纳 5 个话题。用表格写起因、后续发展与争议，每项附 2–3 个代表链接。④、⑤ 表格每格一两句话，单元格长度按榜单配置检查。

### 3.8 洞察

根据 ②–⑤ 提炼 2–3 条有依据的趋势或判断，放在 ① 后。每条写一句话结论、支撑它的周报条目，以及 1–2 篇必读的原始材料和阅读价值。

### 3.9 数据说明

[finalize.py](../工程/scripts/finalize.py) 从采集报告、榜单数据和搜索记录填入各来源状态、数据覆盖、跳过情况和搜索次数。模型补充降级与缺失、AI 改判的原因，以及可疑内容的来源链接。

### 3.10 通用写作规则

事实与链接应有采集结果或搜索证据。只有媒体报道的标注「仅媒体报道」，时间存疑的标注「日期待核实」，媒体转述的数字标明来源。降级版保留榜单数字、文章候选和数据说明，未完成的正文标「本期降级，未生成」，元数据与通知均标明降级。何时发降级版见第 7 节。

## 4. 月报（规划）

汇总该月各周的核心内容，重点是判断和归纳。原规划包含月度主线、发布时间线、按每周新增 star 汇总的月度榜、话题演变、趋势判断和精选必读。使用周报和保存的每周榜单数据作为输入。

## 5. 季报（规划）

综合该季度的月报、周报与榜单数据，归纳重点发布、技术方向、开源与产业趋势，回看上季判断并列出下一季度观察点。正式版的 GitHub 部分汇总各周新增 star。回顾版可用 Trendshift 历史周榜的上榜次数和名次，需注明口径。

## 6. 数据源与 GitHub 榜单

### 6.1 采集信息源

Trendshift 提供榜单与增量，OSS Insight 补充仓库信息，HN Algolia 提供本周讨论，Hugging Face 提供论文候选。第三方页面或接口变化会影响覆盖，缺失情况记录在数据说明。

### 6.2 搜索信息源

优先用官方公告、论文、代码仓库和监管原件。英文科技媒体、个人技术博客、HN 讨论和 YouTube 可补充背景与传播分析。中文媒体和 Newsletter 不纳入取材。完整清单见[来源配置](../工程/config/sources.yaml)。

### 6.3 GitHub 热度榜算法

实际阈值、个数和重试上限见[榜单配置](../工程/config/ranking.yaml)。计算见[排名脚本](../工程/scripts/rank_github.py)，数据校验见[校验脚本](../工程/scripts/validate.py)。

1. **选候选**。以报告周的 Trendshift 周榜为候选，周榜一般约 25 项，榜外项目只可能作为 HN 热议补充。周榜未就绪时先写其他板块，按手册重试；仍未就绪就在 ③ 说明。
2. **判定 AI 相关性**。涉及大模型、智能体、训练推理、RAG、MCP、AI 编程或多模态生成等的项目可入选，拿不准则保留。没有新信息时沿用往期 AI 判定及手工排除。合集、纯链接和越狱提示词合集手工排除；归档、fork、仓库不存在或疑似刷星按当周数据重算。
3. **计算增量与排除**。对仓库页上对应 7 个 UTC 日期的每日新增 star 和 fork 求和，时段比北京时间周界晚 8 小时，数据保持原 UTC 日期。记录覆盖天数；完全缺数据时保留空值。先为增量靠前、新晋候选及 HN 热议项目补查 OSS Insight，再补查因排除递补入选的项目。疑似刷星须同时满足新增 fork/star 比率低于阈值、未关闭 issue 不高于阈值。补查失败记为未核查。
4. **排名与保存**。按新增 star 降序，无增量数据的项目排在有数据的项目之后。同分先看新增 fork，再看 Trendshift 名次，取 Top 5。新晋项目按报告周周日向前的创建天数判定，从未入榜项目中按同一排序选取。HN 热议项目基于 HN 分数，且未列在 Trendshift 周榜。保存所有周榜候选、排除原因和入选的 HN 补充项目至 `数据/github-weekly/{WEEK}.json`。Trendshift 仓库页仅带约 61 天的每日数据，回溯按手册优先复用已存档的榜单数据。

## 7. 质量门槛

- [validate.py](../工程/scripts/validate.py) 核对结构、元数据、链接、榜单及 HN 原文和数字。[check_run.py](../工程/scripts/check_run.py) 还检查运行步骤、产物是否齐备且属本轮，以及搜索次数是否落在[运行时配置](../工程/config/runtime.yaml)范围内。降级版免搜索下限，仍受上限约束。
- 发布时的质量标记由脚本按检查结果和元数据推导。通过记 `full`。结构完整但返工后仍未通过可标 `check_failed` 发布，提交说明和通知标明「检查未通过」，主标题沿用原样。写作中断或正文残缺按降级稿处理。检查无结果，或保留远端人工修改的稿件时，标记 `check_failed` 与 `GATE_UNVERIFIED`。
- 回溯的质量覆盖只豁免材料早于本次运行（`GATE_STALE`）。缺材料、搜索不足和结构错误仍需处理。返工、发布和补交付的实际步骤见[执行手册](../工程/prompts/weekly.md)。
