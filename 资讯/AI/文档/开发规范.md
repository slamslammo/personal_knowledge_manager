# 开发规范

本约定适用于 AI 周报的脚本、配置、提示词和文档。工程结构、依赖与测试命令见[工程 README](../工程/README.md)。

## 实现约定

- 采集、排名、格式校验、发布和重试由脚本执行。模型负责核实来源、选题、分析和写作。可配置的参数放在[工程配置](../工程/config/)。
- 文件位置和命名沿用现有路径函数。工作目录的查询、清理和归档统一用目录工具，保留跨运行状态与交付收据。[路径定义](../工程/scripts/paths.py) · [目录工具](../工程/scripts/workdir.py)
- [固定入口](../工程/prompts/routine-prompt.md)负责指引、授权、安全和失败通知。调整运行步骤改[执行手册](../工程/prompts/weekly.md)，演练参数按本次运行传入。修改入口的授权或安全规则，在 PR 中单列差异供维护者确认。

## 提案与 PR

从最新 `main` 建分支。修复已有规则下的缺陷、改文案或修链接，直接开小 PR，写清问题、改动和验证结果。

改变周报口径、数据源、脚本接口、产出或发布与失败处理规则时，先用[短提案](提案/模板.md)写清改法、影响和验收条件。维护者确认取舍后，更新实现、测试和对应规格。方案待讨论时可开草稿 PR。

## 评审、验收与合并

- 先用离线样本复现，再核对修复和相关失败分支。评审看最终差异和测试结果，开发与评审按当次分工安排。
- 工程目录或 CI 工作流有变更，确认最终提交的[自动测试](../../../.github/workflows/ai-weekly-tests.yml)通过。纯文档变更未命中 CI 路径时，核对链接、命令和 `git diff --check`。
- 工程、配置和文档由维护者合并 PR 或授权合并。当期周报、榜单和运行状态由 `coord.py` 按运行授权发布。人工修复状态文件须走 PR 并说明原因。
- 合并后，下次正常运行读取最新 `main`。交付行为有改动时按需做沙箱验收，正式交付分别核对 Git 提交、飞书正文、通知接口收据与实际收件。生产触发、排程和平台切换由维护者决定。[部署与验收](部署指南.md#验收与切换)
