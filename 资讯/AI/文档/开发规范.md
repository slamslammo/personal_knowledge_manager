# 开发规范

适用于 AI 资讯的脚本、配置、任务手册和开发文档。本地依赖与测试命令见[工程 README](../工程/README.md)。

## 实现约定

- 脚本负责采集、排名、校验、发布与重试。模型负责核实来源、选题、分析和写作。可调参数放在[工程配置](../工程/config/)。
- 文件位置、命名、清理和归档使用现有[路径定义](../工程/core/paths.py)和[目录工具](../工程/core/workdir.py)，保留跨运行状态与交付收据。
- 各类报告的固定入口负责指引、授权、安全和失败通知。运行步骤写在对应的[执行手册](../工程/prompts/)，演练参数只随本次运行传入。入口授权或安全边界有变化时，在 PR 中单列差异。

## 提案与 PR

从最新 `main` 建分支。按现行规格修缺陷、文案或链接，直接开小 PR，写明问题、改动和验证。值得复用的故障结论可写回相关提案。

改变内容口径、数据源、脚本接口、产物或发布行为时，按以下顺序处理。

1. **提出。** 在[版本规划](版本规划.md)登记目标、提出日期和状态。在[提案目录](提案/README.md)用[短模板](提案/模板.md)记录问题、可行选项、取舍和验收办法，两处互链。可在个人目录起草，供团队实现的定稿应在仓库中可查。
2. **实现。** 维护者确认取舍后，修改实现和测试。在同一个 PR 里把生效规则写回[方案](方案.md)，在开头记生效日期和关键变化。涉及操作或代码位置时，同步对应手册或工程导航。
3. **收尾。** 给原提案补上结果、证据和剩余事项，在版本规划登记实际完成日期、PR 或发布稿。实现合并、沙箱通过、正式交付可以发生在不同日期，状态按取得的证据填写。后续方案取代旧选型时，在旧记录中链接接替它的决定。

## 评审、验收与合并

- 先用离线样本复现，再核对修改及相关失败路径。工程目录或 CI 工作流有变更，查看最终提交的[自动测试](../../../.github/workflows/ai-weekly-tests.yml)。纯文档变更核对链接、命令和 `git diff --check`。
- 工程、配置和文档由维护者合并 PR 或授权合并。周报、榜单和周运行记录由周报发布脚本写入，月季报由各自的发布入口只写当期正文。人工修复运行状态须走 PR 并说明原因。
- 发布行为有变化时先做沙箱验收。正式交付分别核对 Git 发布稿、年度表摘要与链接、通知 API 收据（`NOTIFY=sent` / `api_accepted` + `message_id` 即发送成功，不查询送达或已读）。生产触发、排程和平台切换由维护者决定。[部署与验收](部署指南.md#验收与切换)
