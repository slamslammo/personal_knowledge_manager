# AI 资讯部署与排障

## 当前运行

**WorkBuddy 是唯一运行端，当前生产由用户在本机手动触发。** 运行时保持设备开机、WorkBuddy 登录和网络可用。GitHub Actions 只跑 CI。实际模式以 [deployment.yaml](../工程/config/deployment.yaml) 和本次测试参数为准。周报通过 [固定入口](../工程/prompts/routine-weekly.md)进入[周报手册](../工程/prompts/weekly.md)，`deployment.py plan` 显示周报的 `RUN_MODE`。月报和季报单独手动触发，各自使用[月报入口](../工程/prompts/routine-monthly.md)或[季报入口](../工程/prompts/routine-quarterly.md)。开发改动见[开发规范](开发规范.md)。

## 提示词维护约定

固定入口 `资讯/AI/工程/prompts/routine-weekly.md` 是「AI 资讯周报」任务的提示词**唯一真值源**，任务里配置的 prompt 是它的全文副本。修改入口（授权、安全规则或路径）走 PR 合并后，须在 WorkBuddy 任务配置里把新全文重新粘贴一次：**先合并仓库、后同步任务**；回退迁移时先回滚任务 prompt 再 revert。回溯或一次性任务是「入口 + 追加参数段」的变体，应注明基于哪个提交。当前周报按执行手册的三段式运行（`prepare.py` → 智能段 → `deliver.py`），入口本身不含步骤编号，手册更新不要求改入口。

## 环境与授权

在仓库根目录运行 `python3 资讯/AI/工程/core/env_check.py check`。确认运行端的 PATH 能找到 Git，实际使用的 Python ≥3.10 且已安装 PyYAML。安装方式、版本和配置步骤见 [env-bootstrap.md](../工程/prompts/env-bootstrap.md)。

- **Git 与网络**。优先复用该仓库的现有写入身份。缺权限时由用户在平台安全设置提供仅本仓库所需的写入身份。dry-run 是初筛，以协调脚本实际推送为写入证据。保留有效代理、CA 和 TLS 校验，分别核对 GitHub、采集来源和飞书的可达性与权限。
- **飞书**。Node.js 和 lark-cli 用于交付。复用「小龙虾1号」`cli_a92390bc96f9dbb4` 和已授权的同一 CLI 配置。年度表索引用 user，通知用 bot。缺配置时按部署引导给出官方链接或二维码，由本人选择已有应用并完成授权，再回到同一环境完成凭据保存。凭据只通过平台安全设置或官方授权流程提供，禁止回显或入库。遇审批拒绝按实际限制报告。
- **跨任务凭据**。启用无人值守前，检查 CLI 实际配置和数据目录能否安全持久化并回写刷新结果，包括加密主密钥与 DPoP 状态。按部署引导用 `credential_probe.py` 核对独立任务免扫码读取、自然到期后首次 API 刷新、后续任务继承刷新结果。非敏感观察与凭据分开保存。

## 验收与切换

| 场景 | 如何判定 |
| --- | --- |
| 周报首次沙箱验收 | `env_check.py check --require-delivery` 通过后才开始新生成。核对质量检查、沙箱提交与候选稿的字节比对，检查通知预览并保留 `deployment.py finish` 结果。采用 [执行手册的测试模式](../工程/prompts/weekly.md#运行模式)，保存的入口保持固定。 |
| 月季报沙箱验收 | 按[月报手册](../工程/prompts/monthly.md)或[季报手册](../工程/prompts/quarterly.md)运行，两次调用均带 `--test`。核对 `PUBLISHED=ok`、`test=1`、提交号、本地 `published.md` 与通知预览，并确认 `INDEX=skipped NOTIFY=skipped`。 |
| 正式交付 | 分别记录 Git 发布 SHA 与质量结论、年度表记录与 GitHub 正文链接、通知 API 收据和接收人确认。Git 发布成功后，按索引和通知各自的结果补交付。周报另核对归档。 |
| 长期运行或换平台 | 先在目标平台做沙箱验收。用户决定何时正式运行和是否启用调度。切换前暂停旧端的触发、队列与重试，确认在途任务及年度表更新、通知子进程全部结束。凭据续期和真实定时触发需在对应平台单独留证。 |

核心就绪标记仅缓存依赖检查。Git 锁在发布时释放，切换时务必确认飞书也已结束。沙箱通知按规则跳过。沙箱结果、GitHub 写入、正式收件和跨任务刷新逐项报告。

## 补交付

保留原工作目录、期间编号、运行模式和收据。同一模式中已有 Git 发布时只恢复交付。沙箱验收使用本地提交，正式发布以 GitHub 提交为准。命令在对应运行环境的仓库根目录执行。

- **已有沙箱**。配置和授权齐备后，按 [执行手册](../工程/prompts/weekly.md) 的恢复分支运行 `deployment.py resume`。`RESUME=pending` 时保留产物并解决缺项，`RESUME=not_available` 时先核对模式与原沙箱是否仍在。
- **已发布 Git 稿**。用 `python3 资讯/AI/工程/core/annual_index.py --period <期间> --sha <完整发布SHA>` 单独修复索引。检查 INDEX 读回结果。通知结果不明先核对收件。月季报使用同一期间工作目录重试，脚本据发布 SHA 和已有通知收据决定是否补发。当前若发送前返回 `FEISHU_CONFIG_MISSING`，修好配置后仍可能被待确认标记挡住，见[已知问题](https://github.com/slamslammo/personal_knowledge_manager/pull/37#discussion_r4677321694)。
- **指定周正式重跑**。在 production 模式下从最新 main 进入周报执行手册，指定 `--week YYYY-Www`，本次调用不带测试覆盖。由协调脚本根据现有状态决定校验或重跑，按 PREPARE 输出继续。核对本周 Git 正文、年度表摘要与链接，以及通知。具体待跑期间见[版本规划](版本规划.md)。

## 排查和回溯

```bash
python3 资讯/AI/工程/core/trace_view.py --local --errors
python3 资讯/AI/工程/core/trace_view.py --week "<YYYY-Www>" --errors
python3 资讯/AI/工程/core/tracelog.py codes
```

- 查本次工作目录用 `workdir.py print`，其中的 `checks.txt` 记录质量检查，INDEX 输出与 `feishu-notify-receipt.json` 分别记录年度表与通知结果。阻塞或失锁时按执行手册退出，保留现场。运行状态需要人工修复时走开发流程，避免删除历史状态来重试。
- 回溯在单次运行设置 `TARGET_WEEK=YYYY-Www` 或 `TARGET_START=YYYY-MM-DD`，沿用实际运行模式。缺历史榜单时在报告中注明。
- 平台取舍与旧实验见 [运行平台定案](提案/2026-11-17-运行平台三场景验证与定案.md)。
