# 部署指南

**当前运行决定（2026-11-18）：WorkBuddy 本机为唯一运行者，已批准 production，仅由用户手动触发，不启用定时调度。** Codex 保留开发与评审角色，GitHub Actions 运行 CI。本机手动成功不代表跨任务凭据或无人值守验收通过。

普通运行只按 [weekly.md](../工程/prompts/weekly.md)，缺依赖或授权转 [env-bootstrap.md](../工程/prompts/env-bootstrap.md)。本文只维护平台前提、验收证据和异常恢复，不再复制整套生成命令。

## 1. 设计原则

- **确定性与判断力分离**：路径、文件名、数据格式、命名规则、清理与归档由脚本单一真值源固定；智能体只按提示词执行步骤、验证结果，仅在需要分析、总结、判断、写作时使用 AI 能力。详见 [开发原则.md](开发原则.md)。
- **运行时根可预知**：默认由 `REPO_DIR` 推导到仓库检出目录父级的 `.ai-weekly/`，本机与云环境同一条规则；部署级覆盖只用 `AI_WEEKLY_HOME`。查询用 `python3 资讯/AI/工程/scripts/workdir.py print`，不在提示词里写路径；路径不合法时显式失败，不回退 `/tmp`。
- 固定入口只做项目指引、稳定授权和安全边界。部署步骤、版本、格式及模式由项目维护，不为测试临时修改保存的入口。
- 读取实际 `RUN_MODE`，不靠文档里的默认值猜模式。新运行统一经 `deployment.py start`；`plan` 仅报告计划，不能替代启动。
- Git 是生产基础，飞书可分级降级。核心依赖或 Git 写入失败才阻断 Git 周报；飞书 CLI、身份、网络失败不阻正式 Git 生产。
- 分别记录 Git 发布、正文读回、通知 API 接受、实际收件、凭据继承与刷新。就绪标记和一次成功均不能替代其他验收。
- 任何时刻仅一个运行者。发布后释放的 Git 锁不覆盖飞书交付，不能靠错开时间同时启用两端。

## 2. 部署前提

| 能力 | 核实事项 |
| --- | --- |
| Shell、Python ≥3.10、PyYAML、git | 核心生产依赖；在仓库根目录运行 |
| Git 写入身份和联网 | 优先复用平台授权；dry-run 仅初筛，协调脚本实际推送才是写入证据 |
| 搜索及采集来源 | 完整版满足项目搜索范围；受限时按手册记录 check_failed 或降级，不虚报完整性 |
| Node ≥18、lark-cli | 仅飞书交付依赖，版本及安装步骤由 bootstrap 维护 |
| 飞书应用与 user/bot | 复用“小龙虾1号”，核对激活 App ID；user 文档、bot 通知分别实测 |
| 可回写的凭据保存机制 | 长期无人值守的前提，覆盖 CLI 配置、加密主密钥、DPoP 与后续刷新状态 |

缺 Git 身份时由用户在平台安全设置提供仅本仓库写权限的身份或细粒度 token，不强制 classic repo PAT。凭据不发聊天、不入 Git、不回显。保留有效代理、CA 和 TLS；放行实际依赖源、必要下载主机、GitHub、飞书与采集来源，网络可达和服务权限分别验证。

已有飞书配置或授权直接复用；确实缺失时才按 bootstrap 展示官方确认链接/二维码，由本人选择已有应用并完成 user 授权。安装 CLI 不会自动弹出用户本机授权窗；点击确认后仍须在原环境完成设备码轮询和凭据保存。遇审批拒绝时报告依据与范围，不换包装命令或底层接口绕过。

## 3. 开发验证与项目开关

工程变更按 [协作契约 2.1](协作契约.md#21-一轮评审与收口) 走 PR。代码、配置或 workflow 改动要求最终 PR head 对应 CI 绿；未命中自动 CI 路径的纯文档改动做一致性、命令及链接检查，不冒充跑过 CI。

离线开发检查：

```bash
python3 -m unittest discover -s 资讯/AI/工程/scripts/tests -t 资讯/AI/工程/scripts/tests
python3 资讯/AI/工程/scripts/check_portability.py
```

一次性验收演练按 weekly 的测试覆盖规则处理，不改生产配置或任务入口；普通运行按实际计划分支。

## 4. 平台适配

### 4.1 当前配置

| 项 | 当前决定 |
| --- | --- |
| 主运行者 | WorkBuddy 本机，仅手动触发，运行时开机并登录 |
| 仓库与模式 | slamslammo/personal_knowledge_manager，main；每次读取项目实际模式 |
| 入口与平台标识 | 固定 routine-prompt 读取 weekly；记录 `--platform workbuddy` |
| 调度 | 未启用，不创建或激活定时任务 |
| 其他平台 | Codex 开发/评审；GitHub Actions CI，不作为并行生产运行者 |

### 4.2 其他平台与历史方案

[三场景验证与定案](提案/2026-11-17-运行平台三场景验证与定案.md)记录平台取舍；[云端验收修复](提案/2026-11-16-云端定时任务验收修复.md)保留早期部署经验。历史时刻、多平台方案与入口截图不视为当前配置。

### 4.3 未来云端重新验收

当前不部署云端定时任务。用户以后明确选择新运行者时，先排空本机，再按实际平台核对仓库版本、网络、写入身份、入口来源及持久状态机制。发布环境快照不等于 token 刷新可回写，继承字段缺详情不等于已绑定；其他会话的凭据也不会自动转移。无需为云任务额外建立 cron 或再装一层智能体 CLI。

新平台先做隔离验收并记录真实环境来源与运行链接，再另行决定正式手动验证和长期调度。手动触发只能证明入口可执行，真正的定时触发另验，不在历史步骤中直接恢复旧调度。

### 4.4 本次沙箱判据

实际计划为 acceptance；严格机器检查通过后生成，完整性/质量门槛和本地沙箱发布可核对；飞书为 [测试] 文档且读回一致；通知跳过并输出预览；`deployment.py finish` 报告本次结果。沙箱成功不等于 GitHub 写入、真实通知或 C9 已通过，也不会自动启用生产。

### 4.5 正式运行判据

保留完整发布 SHA、状态与质量门槛、飞书文档 ID/正文读回结果、通知 API 收据及接收人确认。质量不合格或交付降级须如实记录。跨任务凭据与刷新另观察；当前手动生产不冒充无人值守通过。

### 4.6 单运行者约束

停止旧端的调度、排队、自动重试与手动入口；确认旧任务及同步子进程全部结束，保存 Git、飞书和未决结果，再启用新端。恢复原端反向执行，任何时刻仅一个运行者；切换后重新观察新平台的凭据状态。

### 4.7 WorkBuddy 本机主运行者

本机验证使用已安装 PyYAML 的 Python ≥3.10；此前可用路径为 `/opt/homebrew/bin/python3.11`，不要默认 Xcode 的 Python 3.9 或未装依赖的内置解释器可用。平台模型在设置中选择可用型号，代理和飞书授权按现场结果检查；漏周按第 5 节回溯。

### 4.8 飞书同步、通知与补交付

使用对应运行保存的工作目录和模式，测试覆盖沿用 weekly；不同模式的旧协调记录不可混用。补交付不重新采集或写稿。

**已有沙箱**：完成本人授权及凭据落盘后，在原环境按 weekly 的恢复分支执行 `deployment.py resume`。completed 报告后结束；pending 保留全部产物，只处理实际缺项；not_available 先核对模式和原文件，不假定其他会话有相同文件。

**已发布生产稿**：先取得应交付的完整 SHA 和 ISO 周，在对应生产上下文替换下列占位符。不要省略 SHA 回退到本地 main。

```bash
S=资讯/AI/工程/scripts
python3 $S/feishu_sync.py sync --from-published --sha "<完整发布SHA>" --week "<YYYY-Www>"
python3 $S/feishu_sync.py verify --sha "<同一完整SHA>" --week "<YYYY-Www>"
```

写接口 created/updated 后才做正文核对；若仅有临时读回失败，直接重试只读 verify，必要时加 `--doc <ID>`，不重复覆盖。READBACK=passed 才报告正文一致；pending/failed 不回滚 Git，通知用 GitHub 链接并注明。保留 `feishu.json`、`feishu-delivery-check.json` 与 `feishu-notify-receipt.json`；收据中的 API 接受/消息 ID 不等于实际收到或已读。

**新建结果不明**：保留 unknown 记录和原上下文。搜索为空、分页未完成或接口报错都不能证明未创建，不删/改本地状态后再次新建。后续搜索唯一命中时由同步复用文档；多候选先人工消歧。若已用独立证据确认文档不存在，将证据交维护者制定明确恢复方案；当前没有清除不确定状态的 override 命令，不以删除记录代替恢复。

**通知结果不明**：先查接收情况。确需重试时使用原周上下文及原样通知文件，沿用该运行模式；示例为对应生产运行的原文件：

```bash
python3 资讯/AI/工程/scripts/feishu_sync.py notify --file "$W/notification.txt" --fallback-file "$W/notification-short.txt"
```

不得改正文或换精简版来规避幂等；缺原文件/上下文时先报告。确定拒绝的通知由脚本按规则兜底。API 接受与接收人实际确认分别记录。

### 4.9 环境清单与验收

| 项 | 核对方式与结果边界 |
| --- | --- |
| C1 Git 写入 | 复用已有身份、dry-run 初筛、真实协调推送 |
| C2 Node / CLI | 记录实际版本，仅交付依赖 |
| C3 路径 / profile | 核实 wrapper、PATH 及实际 config/data/logs，不完整回显配置 |
| C4 应用绑定 | 当前激活 App ID 必须是 cli_a92390bc96f9dbb4 |
| C5 bot / C6 user | 服务端鉴权与实际通知/文档操作分别验证 |
| C7 身份边界 | 文档显式 user、通知显式 bot，不要求 bot 建文档必须失败 |
| C8 网络 | 保留有效代理与 CA，以实际鉴权及文档读写验证 |
| C9 持久化与刷新 | 独立任务免扫码、自然到期后首次 API 刷新、后续任务继承新状态分项留证 |

C9 使用 `credential_probe.py --resume` 或 `--doc <测试文档ID>` 观察；状态默认 `~/.local/state/ai-weekly/`，可配 `AI_WEEKLY_STATE_DIR`，只含非敏感观察，不保存或搬运凭据。实例线索须结合平台运行记录，同实例重跑、静态快照和本地 auth status 都不能证明跨任务刷新可用。每周间隔贴近已观察到的约 7 天 refresh 期限，长期启用前验证提前续期与回写机制。

C.1/C.2 均按实际平台逐项记录；C.3 的判据是当前手动运行分项验证、未来调度另行批准；C.4 切换遵循 4.6。历史云端通过不自动适用于本机。

### 4.10 核心就绪标记与验收状态

`env_check.py ensure` 仅缓存核心依赖，输出 core_ready 不表示交付验收。`check --require-delivery` 是首次验收新生成的严格机器门槛，失败时 deployment start 输出 ACTION=blocked，不进行采集和写稿。人工项和 C9 保持独立 pending，正式模式继续遵守飞书降级边界。

### 4.11 当前本机手动生产与验证

日常仅按 weekly 的推荐链路处理初始 ACTION；无运行资格就不生成。已发布后只补交付/只读核对。C9、后续当周观察及收件确认按证据更新，不因整理文档改配置、重跑周报或启用调度。W45 过程与可核验范围见 [复盘](提案/2026-11-18-迁移与生产发布复盘.md)。

## 5. 回溯运行

一次性会话可显式指定 `TARGET_START=YYYY-MM-DD` 或 `TARGET_WEEK=YYYY-Www`；不改保存入口，报告周由 weeks.py 解析。缺历史榜单时注明局限，回溯不会绕过项目模式及交付隔离。

## 6. 故障排查

先区分本地未发布问题和远端运行记录：

```bash
python3 资讯/AI/工程/scripts/trace_view.py --local --errors
python3 资讯/AI/工程/scripts/trace_view.py --week "<YYYY-Www>" --errors
python3 资讯/AI/工程/scripts/tracelog.py codes
```

| 现象 | 处理 |
| --- | --- |
| 核心依赖缺失、Git 写入拒绝 | 转 bootstrap；核对身份、分支策略与网络，未取得锁不进入生成 |
| STATE_INVALID / 需人工 | 保留状态历史，交维护者复核并按开发流程修复，不用删除状态文件当重试按钮 |
| ACTION=lost | 没有本轮发布，跳过同步，按 weekly 发未提交通知；不假定另一个平台会兜底 |
| GATE_SEARCH_MIN / GATE_INCOMPLETE | 按 weekly 补缺项；完整版、check_failed、降级结果如实区分 |
| 来源超时、403、周榜未就绪 | 按 weekly 有限重试或注明降级，不虚构来源可达 |
| 飞书身份或网络失败 | Git 不回滚；补齐对应交付缺项，按 4.8 对同一发布 SHA 恢复 |
| FEISHU_AMBIGUOUS_DOC | 人工确认目标文档，再补交付，不盲目覆盖 |
| FEISHU_SYNC_UNKNOWN / 未决新建后的 FEISHU_SYNC_FAILED | 按 4.8 保留 unknown；零命中或接口失败均不允许清状态重建 |
| READBACK=pending/failed | 保留同步结果，先重试只读核对，不改写成已验证 |
| FEISHU_NOTIFY_UNKNOWN / FAILED | 按 4.8 分清是否送达不明，保留原正文和周上下文后决定重试 |
