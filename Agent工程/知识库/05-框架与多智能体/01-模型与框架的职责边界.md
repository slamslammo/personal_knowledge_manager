# 模型与框架的职责边界

## 定位

本节回答：智能体的行为中，哪些由模型决定、哪些由框架决定；更换模型与更换框架时，分别有哪些行为会改变、哪些不会。本板块把模型之外、驱动智能体循环运行的程序统称为框架，工程实践中也常称为 harness，教材仓库的参考答案称之为“外部执行器”（Extra01）。

前置：工具调用的基本机制——模型给出调用声明，由程序执行（4.2.2、7.5），本节不再展开。

文中的“教材”指核心材料 Hello-Agents，小节号（如 2.4.5）为教材的章节编号；引用写法与版本见[参考资料](node:refs)。

## 核心解释

在智能体循环的每一轮里，模型只做一件事：**在给定的输入下，决定下一步**——调用哪个工具、传入什么参数，或者给出什么回答。除此之外的事情都由框架完成：输入里放什么，声明如何被识别和执行，结果怎样回到下一轮输入，什么时候停下，留下什么记录。教材在第 4 章引言中列举的框架职责——解析模型输出格式、重试失败的工具调用、防止智能体陷入死循环——都属于后一类。

按循环中的环节，两侧的分工如下〔待核验〕：

| 环节 | 模型决定 | 框架决定 |
|---|---|---|
| 看到什么 | 如何理解给到的内容 | 系统提示词、工具描述、历史、笔记与检索结果如何装配进输入 |
| 能做什么 | 在可用工具中选择哪一个 | 提供哪些工具，工具如何描述 |
| 声明如何被识别 | 输出是否符合约定 | 采用提示词约定格式还是原生函数调用，解析失败如何处理 |
| 如何执行 | — | 执行、超时、权限与错误处理 |
| 结果如何回来 | 如何解读结果 | 截断、告知、落盘与返回状态 |
| 何时停止 | 是否给出完成信号 | 如何识别完成信号，预算与失败上限 |
| 留下什么 | — | 任务状态与运行轨迹的记录 |

据此可以回答“换一侧，变什么”：

- **更换模型**，改变的是同样输入下的决策质量：推理与规划能力、指令与格式遵循、工具选择与参数的准确性、模型自身的知识。**不变**的是模型能看到的信息、可用的动作、声明的识别方式、结果的回填方式与停止规则。因此，框架层面的缺陷不会因为换模型而被修复，只可能因为更强的模型更少触发它而被掩盖〔待核验〕。
- **更换框架**，改变的是模型所处的条件：输入由什么构成、可以采取哪些行动、调用如何被识别、结果如何回来、何时停下、中断后能否继续。**不变**的是模型面对同一份输入时的决策能力。因此，同一个模型换一个框架，表现可能明显不同。教材给出了直接的例证：原生函数调用比依靠提示词约束格式更鲁棒（7.4.5）；在 BFCL 评估中，使用自定义调用格式的 SimpleAgent 在复杂场景下的表现，可能不如使用原生函数调用的智能体（12.2.6）。

两侧并不独立。教材指出，并非所有模型都能持续稳定地遵循预设格式（4.2.4）；而框架如何处理格式偏差，决定了这种模型差异在结果上被放大还是被吸收——同样一次格式错误，在不同实现中可能被回传修正、被当作完成，或者引发原地重复（教材代码分析，见[终止判定的漏判](node:terminate)）。

这条边界也是[工具结果处理](node:toolresult)结论的延伸：模型只输出调用声明，大结果如何交还给模型由框架决定，所以更换框架就改变了模型所能拿到的证据，也就改变了智能体的能力边界。

## 机制深挖

### 教材改进手段的归属

教材在调试 ReAct 与提升 BFCL 分数时给出的建议，可以按两侧归类（建议出自教材正文；归入哪一侧由本板块判断〔待核验〕）：

| 建议 | 出处 | 所属一侧 |
|---|---|---|
| 更换能力更强的模型，或调整采样温度（temperature） | 4.2.4 | 模型 |
| 改用支持原生函数调用的模型 | 12.2.6 | 两侧都涉及：需要模型支持，也需要框架改用该协议 |
| 打印完整提示词，追溯决策依据 | 4.2.4 | 框架（提示词由框架拼装） |
| 验证工具的输入输出格式 | 4.2.4 | 框架（工具与结果回填） |
| 在提示词中加入示例 | 4.2.4 | 框架 |
| 扩展工具库，针对不同类别设计不同策略 | 12.2.6 | 框架 |

提示词归入框架一侧，是因为提示词模板由程序填入工具描述、问题与历史之后才交给模型（4.2.3）。但提示词的效果依赖具体模型：教材同时指出，模板中的微小变动都可能影响模型行为（4.2.4）。这意味着针对某个模型调好的提示词，换模型后需要重新验证〔待核验〕。

### 规则的两种落点：提示词与代码

同一条约束可以放在两侧。写在提示词里（例如“连续失败 3 次就停止”“不要用相同参数重复编辑”），它是否生效，取决于模型是否遵守、是否还记得；写在框架代码里（例如失败计数与熔断、执行危险操作前的强制确认），它不依赖模型的判断。社区补充章节的做法是：关键约束不放进会被压缩的对话历史，高风险操作的确认由代码硬性检查、不交给模型判断（Extra09 第五章）；工具连续失败时，由工具注册层熔断（Extra09 第三章）。把必须成立的约束从模型一侧移到框架一侧，是划分职责边界时的一种重要手段〔待核验〕。

### 更换模型的成本

HelloAgents 选择在 OpenAI 兼容接口之上构建，并支持多个模型提供商与自动检测（7.1.2、7.2）。在这种设计下，更换模型通常只需要改配置，调用方式不变（7.2.3）。这让“只换模型、框架不变”的对照很容易进行；反过来，更换框架往往意味着提示词、工具协议与循环逻辑多处同时改变，对照时更需要控制变量，见[评估设计四要素](node:evaldesign)。

## 与相邻知识点的关系

- [终止判定的漏判](node:terminate)：解析方式与完成信号属于框架侧，漏判是框架侧缺陷的典型表现。
- [工具结果处理](node:toolresult)：大结果处理归框架，是“更换框架即改变能力边界”的直接来源。
- [停止条件设计](node:stopcond)：停止规则由模型遵守，还是由框架强制。
- [任务评估](node:taskeval)：改模型与改框架应当分开评估，才能判断改进来自哪一侧。
