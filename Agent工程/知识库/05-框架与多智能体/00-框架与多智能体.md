# 构建：框架与多智能体

本部分回答：模型、工具、上下文与状态如何组织成一个可运行、可维护的系统；单个智能体不足以完成任务时，多个智能体如何分工协作。

## 主线

手写一个循环就能跑通单个智能体，但工程问题会随任务复杂度迅速增加。教材在第 4 章引言中列举了框架替开发者处理的问题：模型输出格式的解析、工具调用失败的重试、防止智能体陷入死循环等。这些都是模型之外的运行逻辑，由框架承担（工程实践中也常把这层程序称为 harness）。因此，同一个模型在不同框架中的表现可能不同，例如教材 7.4.5 指出，原生函数调用比依靠提示词约束格式更鲁棒。弄清[模型与框架的职责边界](node:responsibility)，是判断问题出在哪一侧、改进应当落在哪一侧的前提。

在此基础上，低代码平台与主流开发框架提供了不同抽象层次的现成方案。现成框架在工程效率上有优势，也有过度抽象、接口频繁变动、内部逻辑不透明等代价（7.1.1）。当任务需要不同专长的角色分工或并行探索时，再进一步引入多智能体协作。
