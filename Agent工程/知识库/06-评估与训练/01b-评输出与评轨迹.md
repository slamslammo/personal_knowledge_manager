# 评输出与评轨迹

## 定位

本节是[任务评估](node:taskeval)的机制深挖，说明评估最终输出与评估执行轨迹各自看什么、为什么两者都需要，以及评估轨迹需要记录哪些内容。

文中的“教材”指核心材料 Hello-Agents，小节号（如 2.4.5）为教材的章节编号；引用写法与版本见[参考资料](node:refs)。

## 核心解释

**输出**是智能体最终交付的结果：一个答案、一份报告、一次修改。**轨迹**是得到这个结果的全过程：每一轮模型收到的输入与给出的输出、发起的工具调用与参数、工具返回的结果、最终的停止原因，以及沿途消耗的 token 与时间。

把两种评估的结论组合起来，会得到四种情况：

| | 轨迹合理 | 轨迹不合理 |
|---|---|---|
| **输出正确** | 可以保留的成功 | 结果对了，但过程靠运气、绕了远路或产生了多余副作用，换一个任务可能就会失败 |
| **输出错误** | 过程基本正确，错在个别环节，轨迹能指出具体位置 | 需要从轨迹中找出最早偏离的一步 |

只评输出，会把右上角当作成功，也无法区分左下角与右下角〔待核验〕。只评轨迹，又容易把“与参考路径不同”误判为错误：教材指出同一问题可能有多个正确答案（12.1.1），完成任务的合理路径同样不止一条。所以轨迹评估更适合检查约束——是否调用了不该调用的工具、是否超出预算、是否出现重复的无效调用——而不是要求与某条参考路径完全一致〔待核验〕。

## 机制深挖

### 教材中的两种视角

| 评估 | 看的是 | 属于 |
|---|---|---|
| BFCL | 给定问题与可用函数，模型给出的函数调用是否与期望一致（12.2.1） | 单步决策，轨迹中的一个环节 |
| GAIA 精确匹配率与分级准确率 | 最终答案是否正确（12.3.1） | 输出 |
| GAIA 平均推理步骤数 | 正确回答的样本平均用了多少步（12.3.1） | 轨迹统计 |
| 效率与鲁棒性指标 | token 用量、响应时间、错误率、故障恢复（12.1.2） | 轨迹统计 |
| 习题中的扩展 | 有依赖关系的多个调用的执行顺序、是否用了最少的调用次数、错误类型分析报告（第 12 章习题 2） | 轨迹 |

BFCL 中判断是否需要调用函数的类别，检验的是“不该调用时不调用”（12.2.1），这是只看最终输出无法覆盖的决策质量。GAIA 样本中标注者记录的推理步骤与所需工具（12.3.1），可以作为评估轨迹时的参考，但不宜要求逐步一致〔待核验〕。

### 只在轨迹中可见的失败

有些失败在输出中完全不可见，或者看起来只是“答错了”：

- **假完成**：格式出错或中途纯文本被当作最终回答，输出表现为一个不完整或答非所问的回答；轨迹中能看到任务在很少的步数内结束，而最后一轮本应是工具调用（见[终止判定的漏判](node:terminate)）。
- **假进行**：同一调用重复出现、观察结果不再变化，最终因预算耗尽而结束（见[停止条件设计](node:stopcond)）。
- **证据不足**：工具结果被截断而没有告知，模型基于部分信息作答（见[工具结果处理](node:toolresult)）。
- **重复与遗漏**：已完成的步骤被再次执行，或计划中的步骤被跳过（见[任务状态](node:taskstate)）。

### 轨迹的记录范围

社区补充章节给出了一个完整的轨迹记录范围：每一轮的模型输入与输出、工具调用参数、工具返回结果与 token 用量（Extra09 第六章），并提出几条设计原则：用结构化数据而不是文本描述记录事件；记录时带上当时的步数、token 用量等上下文；保留失败的尝试，而不是只留最终结果；同时提供便于程序分析与便于人阅读的两种格式。

其中“每一轮模型实际收到的输入”最容易被省略，而它决定了一次错误决策能否被解释——社区补充章节中有一个模型反复误用写入工具的案例，查看完整轨迹后才发现上下文里缺少判断所需的任务信息（Extra09 第四章）。这类判断属于[模型与框架的职责边界](node:responsibility)。
