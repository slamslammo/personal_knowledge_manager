# 任务评估

## 定位

本节回答：怎样可靠地判断一个智能体——或者对它的一次改动——在自己的任务上变好还是变坏。教材在第 12 章开篇提出的正是这个问题：优化提示词或更换模型之后，如何知道是否真的有改进（12.1.1）。

任务评估与公开基准（见[评估与训练](node:evaluation)）的目标不同。公开基准在统一的数据集与评分方法下衡量通用能力，便于横向比较不同系统；任务评估面向自己的任务与自己的改动，回答“这次改动是否值得保留”。两者的方法大量重合：教材中的 BFCL、GAIA 与数据生成质量评估，为任务评估提供了可以直接借用的数据组织方式与判定方法。

文中的“教材”指核心材料 Hello-Agents，小节号（如 2.4.5）为教材的章节编号；引用写法与版本见[参考资料](node:refs)。

## 核心解释

### 单次运行的结论不可靠

教材把智能体评估的独特挑战概括为三点：输出不确定，同一问题可能有多个正确答案；评估标准多样，不同任务需要不同的判定方法；评估成本高，每次评估都需要大量模型调用（12.1.1）。此外，智能体要走多步，每一步的采样结果与工具返回都可能不同，同一个任务两次运行可能走出不同的路径〔待核验〕。一次成功或失败，既可能来自改动本身，也可能只是这一次运行的偶然结果。

### 可靠比较的四个要素

要让“改动前后”的比较有意义，评估需要同时满足四个条件：

1. **固定任务集**：改动前后使用同一批任务。任务应覆盖不同类型，并包含“不应该行动”的反例；BFCL 就专门设置了判断是否需要调用函数的类别（12.2.1）。
2. **基线**：与改动前的版本在相同任务集、相同设置下比较。教材的对比评估示例，正是在同一类别、同样样本数上比较默认提示词与优化提示词两种配置（12.2.6）。
3. **事先确定标准**：在看到结果之前定好判定规则。教材展示了三类自动判定方法——规则匹配（BFCL 的抽象语法树匹配、GAIA 的准精确匹配）、评分量表（以模型作为评审，即 LLM Judge）与成对比较（胜率，Win Rate），以及作为补充的人工验证（12.2.1、12.3.1、12.4.1）。
4. **多次运行**：同一任务重复运行多次，用通过率与波动而不是单次结果做比较〔待核验〕。教材没有讨论重复运行，只在调试建议中提到把采样温度设为 0 以保证输出的确定性（4.2.4）。

### 输出与轨迹

**评输出**看最终结果是否正确；**评轨迹**看过程：调用了哪些工具、参数是否正确、顺序与次数是否合理、消耗了多少 token 与时间、是否产生了不必要的副作用。教材中两种视角都有：BFCL 判定的是单次调用决策是否正确（12.2.1），GAIA 判定最终答案并统计平均推理步骤数（12.3.1），效率指标包括 token 用量与响应时间（12.1.2），习题还要求把评估扩展到调用顺序与调用次数（第 12 章习题 2）。

两者缺一不可：输出正确不代表过程可以接受，它可能靠运气、绕了远路或产生了多余的副作用；输出错误时，只有轨迹能指出从哪一步开始偏离。[终止判定的漏判](node:terminate)这类问题，也只有在轨迹中才能看清。

### 失败集与回归

每次评估或实际使用中发现的失败，都应整理进**失败集**，并补充到固定任务集中。之后的每次改动，都在包含这些失败案例的任务集上重新运行，逐个任务与基线对比，找出“原来通过、现在失败”的**回归**〔待核验〕。教材的实践建议要求分析失败案例、找出薄弱环节（12.2.6），习题进一步提出设计定期运行、性能下降时告警的持续评估系统（第 12 章习题 5）。

### 一次只改一处

改动应当一次只改一个变量，并把“改模型”与“改框架”分开评估；否则即使结果变好，也无法知道是哪一处改动起了作用。社区补充章节的做法是：保持其他条件不变，只改提示词中的一点，在同样的测试用例上记录成功率、步数与 token 消耗，再对比新旧轨迹（Extra09 第四章）。模型侧与框架侧各自负责什么，见[模型与框架的职责边界](node:responsibility)。

## 机制深挖

- [评估设计四要素](node:evaldesign)：任务集怎样组成，基线怎样设置，教材中各类判定方法的规则与局限，以及重复运行的必要性。
- [评输出与评轨迹](node:outputtrajectory)：两种评估各看什么，四种组合分别说明什么，轨迹需要记录哪些内容。
