## 0. 背景

v0.8 阶段一的代码已于 2026-11-09 合并，但**从未在运行环境生效**：`AI资讯/数据/` 下只有 `github-weekly/`，没有任何 `运行记录/{WEEK}.json`，而状态文件是 v0.8 协调锁、独立校验与执行记录的唯一载体。同时 Codex 在评审中复现了「门槛未过的周报仍能以 `full` 发布」，这属于发布侧的结构性缺口，优先级高于补月报、补回溯。

本提案同时把「方案怎么评审、证据留哪里」固定下来（见 `../协作契约.md` 与 `提案/README.md`），之后每轮按同一流程推进。

## 1. 问题与证据

### P0-A：`publish` 的 quality 由模型自填，脚本不校验

- `prompts/weekly.md` 第 5 步让智能体自己决定命令行参数：`coord.py publish [--quality full|check_failed|degraded] [--codes <CODES>]`。
- `scripts/coord.py:848` 该参数 `default="full"`；全文没有任何一处调用 `validate.py` 或 `check_run.py`（`coord.py` 里的 `subprocess` 只用于 git）。
- 也就是说：**门槛过没过，与最终写进状态文件的 `quality` 无关**。`apply_publish()` 只是把传入值原样记进 `produced.quality`（`coord.py:398-406`）。

### P0-B：标记错了不会被发现，因为校验只看标记

- `scripts/verify.py:56` 的逻辑是「`produced.quality` 是 `degraded` / `check_failed` → 需要重跑」；标成 `full` 就直接放行。
- 单平台部署时 `verify.py` 根本不会运行（`方案.md` 13 节自述：只部署一个平台时只能靠没收到通知来发现）。
- 两个缺口叠加：门槛未过 → 标 `full` → 无第二方校验 → 无效周报以「已完成」进入 `main`，且 `verify.py` 事后不会补查。

> 注：`validate.py` 已能识别「标了 `quality: degraded` 的降级版」（`validate.py:228-230`，只允许 `degraded` 或不写）。缺的不是这个方向，而是**「没标 `degraded` 就等于门槛通过」这个默认假设没有人验证**。

### P1：v0.8 未上线（平台侧动作，仓库无法替代）

- `版本规划.md` 第 35 行仍是「待做 | 重贴入口提示词 v3 并改运行时间」。
- `config/task.yaml`、`方案.md` 7.3、`部署指南.md` 4.2 三处口径**已经是周一 10:00**，仓库侧无需再改；差的只是平台上的实际设置与提示词粘贴。

### P2：月报缺手册，两个月的依赖要分开看

- `prompts/monthly.md`、`quarterly.md` 属 v0.2，尚未编写；`AI资讯/月报/`、`季报/` 目录都不存在。
- **10 月月报**（W40–W44）因缺 W40–W42 周报无法生成（W44 数据说明原文已记录）；**11 月月报**（W45–W48）只依赖 11 月各期周报，与 W40–W42 缺失无关。
- 更正我此前的表述：不存在「W40–W42 阻塞 11 月月报」的链式死锁；两个月要分别检查依赖。

### P3：依赖与测试没有固化

- 仓库没有 `requirements.txt`、没有 CI。98 个单元测试只能靠人记得手动跑；`部署指南.md` 只写了「python3（带 PyYAML）」。实测本机四个解释器都没有 PyYAML。

## 2. 方案

### 2.1 P0-A：把 quality 从「模型声明」改为「脚本推导」

- `coord.py publish` 在推送前，以子进程运行 `check_run.py --work-dir <work>`。该脚本已包含 `validate.py` 的全部结构校验与质量门槛（`check_run.py` 直接 `from validate import run_checks`），并在失败时输出 `CODES=...`，因此不需要新增第三套判定。
- quality 推导规则（取消智能体自填）：

| check_run 退出码 | 周报是否降级版 | quality |
| --- | --- | --- |
| 0 | 否 | `full` |
| 非 0 | 否 | `check_failed`（附带解析出的 CODES） |
| 0 或非 0 | 是（元数据含 `quality: degraded`） | `degraded` |

- **降级版判定复用 `validate.py` 的解析**：`coord.py` 读周报元数据用 `validate.split_front_matter` + `yaml.safe_load`，不用正则。否则 `quality: "degraded"` 或行尾带注释这类合法 YAML，`validate.py` 认作降级版并按宽松规则放过，`coord.py` 却认不出来、把同一份周报标成 `full` 发布。
- `--quality` 参数保留，但改为「期望值」：与推导结果不一致时**拒绝发布**，退出码非 0 并给错误码 `GATE_MISMATCH`。回溯、测试模式用 `--quality X --allow-quality-override` 显式按声明值发布（跳过比对，不是跳过记录）：`gates.override` 记下被覆盖的质量，`verify.py` 见到覆盖会写进校验说明，事后能看出这一周的质量是声明的而非推导的。
- `--allow-quality-override` **在代码里限制生效范围**：只有 `week.json` 的 `mode=backfill` 能用，其余一律拒绝并给 `GATE_OVERRIDE_DENIED`。判定不吃 `--test` 标志——`--test` 可以显式指定任意远端（`--remote origin`、生产 URL 都行），按名字排除 `origin` 挡不住，所以测试运行没有这个权限；要覆盖就把 mode 设成 backfill，那本来就是唯一需要它的场景。**并且只豁免 `GATE_STALE`（材料早于本次运行）**：`GATE_INCOMPLETE`、`GATE_SEARCH_MIN/MAX`、`GATE_STRUCTURE` 等说明产出内容本身不合格，与时间无关，一并豁免会让结构错误或缺材料的周报带上 `full`（见 2.3 补充）。
- 覆盖的值必须与周报元数据一致：`--quality full` 只能用于正常版周报，`--quality degraded` 只能用于降级版，否则 `GATE_OVERRIDE_CONFLICT` 拒绝。覆盖的语义是「跳过门槛的新鲜度判断」，不是「改产物本身的质量」；让 `full` 落在降级版周报上，`validate.py` 仍会按降级规则做宽松校验，`full` 名不副实。周报被人工改过时也不允许覆盖（本次提交的不是候选）。
- 只写在文档里不够——单平台部署不跑独立校验，留一个「随时可覆盖」的开关等于把本节的门禁重新打开。
- 状态文件 `produced` 增加 `gates` 字段：`{"check_run": "pass|fail|skipped", "codes": [...], "override": 可选}`，与 `quality` 一起推送，供事后复核。
- **门槛脚本不可替换**：`publish` 固定运行同目录的 `check_run.py`，没有配置项、没有环境变量、没有测试开关能换掉它。曾经为集成测试开过 `publish.gate_script` 注入替身，评审连续指出这条通道等于在生产代码里留后门（`--test` 可以指定真实远端，配上环境变量就能拿一个常通过的替身去打生产），已删除；测试改成用 `tests/fixture.py` 造出「本次运行都做了」的真实产物，跑真门槛——这样测的还是生产路径本身。

### 2.2 P0-B：让校验不再只信标记

- `verify.py`：`produced` 缺少 `gates` 字段时（旧状态文件、或有人手工写入），按 `check_failed` 处理并要求重跑，不再默认放行。
- `verify.py`：`produced.quality=full` 但周报元数据写着 `quality: degraded` 时，记 `GATE_OVERRIDE_CONFLICT` 要求重跑。`run_checks` 是照着周报元数据决定走宽松校验的，光看 `produced.quality` 会以为「按 full 校验过了」；回溯用 `--quality full` 覆盖到降级版周报上正好踩这个坑。
- `validate.run_checks` 新增 `require_full`：`verify.py` 在 `quality=full` 时传 `require_full=True`，让校验按完整周报跑，元数据自称降级也不能放宽。这样「声明 full」这件事本身在校验阶段是可验证的，而不是只在发布时拦一次。
- `verify.py` 已有的重跑门槛逻辑（`:77` 的 `run_checks`）保留不变，作为第二道独立证据。

### 2.3 P0 的失败处理

| 情形 | 处理 |
| --- | --- |
| `check_run.py` 子进程超时（默认 120 秒） | 不阻塞发布，quality 降为 `check_failed`，记 `GATE_UNVERIFIED` |
| `check_run.py` 崩溃 / 输出里没有 `CODES=` | 同上，`GATE_UNVERIFIED`（语义是「没拿到门槛结果」，不是「步骤没做」，不能用 `GATE_INCOMPLETE` 把人引向返工） |
| 远端周报被人工改过，本次不覆盖 | 门槛检的是 OUT_DIR 的候选、提交的是人工那份，记 `gates.check_run=skipped` + `GATE_UNVERIFIED`，quality 按 `check_failed` 发布 |
| 推导结果与 `--quality` 不一致且未加 `--allow-quality-override` | 拒绝发布，`GATE_MISMATCH`，不发通知（由调用方按失败处理） |
| 正式运行加了 `--allow-quality-override` | 拒绝发布，`GATE_OVERRIDE_DENIED`；只有 `mode=backfill` 放行 |
| 回溯覆盖，但失败项里有不可豁免的码（`GATE_INCOMPLETE` / `GATE_SEARCH_MIN` / `GATE_STRUCTURE` 等） | 拒绝发布，`GATE_OVERRIDE_DENIED`，提示先按门槛返工（2026-11-12 补） |
| 回溯覆盖，失败项只有 `GATE_STALE`（材料早于本次运行） | 放行，按声明质量发布；豁免的码记进 `gates.waived`（2026-11-12 补） |
| 覆盖值与周报元数据不一致（降级版声明 `full` 或反之） | 拒绝发布，`GATE_OVERRIDE_CONFLICT` |
| 周报被人工改过，本次不覆盖 | 拒绝覆盖；门槛记 `gates.check_run=skipped` + `GATE_UNVERIFIED`，quality 按 `check_failed` 发布（不看候选的元数据，那份不提交） |
| 加了 `--allow-quality-override` 但没给 `--quality` | 拒绝发布，提示用法错误 |
| 推送被拒 | 沿用现有 7.9 节规则，不改 |

原则不变：**只有「写不出周报」和「提交失败」算整次运行失败**，门槛问题一律降级发布并如实标记。

补充两点（2026-11-12 评审后明确，此前表述含糊）：

- **门槛不阻止推送，只改标记。** 门槛失败、`check_run.py` 崩溃或超时，都是照常发布，`produced.quality` 记 `check_failed`、`gates.codes` 记原因，提交标题带「检查未通过」。真正拒绝推送的只有 `GATE_MISMATCH` / `GATE_OVERRIDE_DENIED` / `GATE_OVERRIDE_CONFLICT` 三类。此前把它说成「崩溃、超时一律不推送」与代码不符，已按代码口径改正。
- **覆盖的豁免范围只到 `GATE_STALE`。** 「材料早于本次运行」可以用人工确认代替重跑；`GATE_INCOMPLETE`（这一步没产物）、`GATE_SEARCH_MIN/MAX`、`GATE_STRUCTURE` 说的是产出内容本身，与时间无关，覆盖成 `full` 会让结构错误或缺材料的周报带上满分标记。为此 `check_run.py` 把「文件在但旧」与「文件不在」拆成两个码，单测固定了这两条。
- **判定顺序：有没有文件 → 内容全不全 → 旧不旧。** 先看新鲜度会把「缺产物」挡在一个可豁免的 `GATE_STALE` 后面（评审复现：`collect_report.json` 旧 + `materials.json` 不在 → 只报 `GATE_STALE` → 覆盖放行、`quality=full`）。采集、AI 判定与排名、草稿三步都按这个顺序判，各有单测。

### 2.4 P1：平台侧动作（用户执行）

1. 把 `prompts/routine-prompt.md` 全文贴进定时任务（v3 白名单含状态文件）。
2. 运行时间从 8:45 改为周一 10:00（依据 `方案.md` 7.3：UTC 周界为北京时间 08:00，留 2 小时缓冲）。

4. 手动触发一次正式运行。

## 4. 验收条件

1. 单测新增 ≥ 6 个：三种 quality 推导、`GATE_MISMATCH` 拒绝、`GATE_UNVERIFIED` 降级、`gates` 缺失时 verify 要求重跑；全套（现有 98 + 新增）通过。
2. 复现验证：构造门槛未过的运行目录，`coord.py publish`（不传参数）后状态文件 `quality=check_failed` 且 `gates.codes` 非空。
3. 测试模式端到端：`coord.py start --test` 全流程通过，模拟仓库里的提交信息与状态流转与 7.9 节一致。
4. 线上验收（P1 完成后）：11-16 运行产出 `AI资讯/数据/运行记录/2026-W46.json`，其中 `produced.quality` 与 `produced.gates` 一致；`trace_view.py --week 2026-W46` 能还原时间线。
5. CI 工作流（另提交）在 PR 与 push 上触发并通过；在此之前以本地 `unittest discover` 结果作为证据。
