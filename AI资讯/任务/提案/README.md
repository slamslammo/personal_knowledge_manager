# 提案

本目录存放 AI 资讯任务每一轮开发的方案，作为**方案评审的唯一载体**。GitHub 上的自动审查只读仓库，读不到聊天记录，所以方案必须先写进这里，评审才有对象。

## 什么时候要写提案

| 情况 | 是否要提案 |
| --- | --- |
| 改流程、改规则、改数据源、改脚本契约、加产出类型 | 要 |
| 修文案、修错别字、补注释 | 不要，直接 PR |
| 只改部署配置（平台侧） | 不要，记入 `版本规划.md` 即可 |

## 命名与状态

- 文件名：`YYYY-MM-DD-<短横线标题>.md`，日期取提出当天。
- 状态按顺序流转，写在文件开头的元信息里：

```text
草案 → 评审中 → 已批准 → 实施中 → 已完成
                                   ↘ 已放弃（写明原因）
```

- 提案批准前不改代码；实现完成后不要把提案删掉，保留为决策记录。`方案.md` 是被批准规则的正式文本，提案只记录「为什么这样改」。

## 评审记录

每个提案末尾有一张评审记录表，每次评审追加一行：日期、评审方（Codex / 用户）、结论、对应提交 SHA。追加提交后需要复审时，在 PR 评论 `@codex review`。

## 与其它文档的关系

| 文档 | 作用 |
| --- | --- |
| `提案/` | 单轮方案与评审记录，一次评审一个文件 |
| `../方案.md` | 被批准的规则正文，规则的唯一权威表述 |
| `../版本规划.md` | 版本路线与「何时、为什么改」的迭代记录 |
| `../部署指南.md` | 平台侧配置与验收步骤 |
| `../协作契约.md` | 谁做、按什么门禁做、证据留哪里 |
