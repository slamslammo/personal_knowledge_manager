## 1. 定案（四条，不变）

1. **单运行者**：云端（Codex）是唯一活跃定时任务（周一 10:00）。WorkBuddy 定时任务**创建即暂停**（PAUSED），仅在云端失效时按 C.4 规程启用替补——同一时间永远只有一个运行者，无并发。
2. **锁：不设计、不改动**。现有 `coord.py` 锁代码保留原样；飞书已实测无锁原语（附录 A.2），不引入任何新锁机制、不加开关。
3. **协调与幂等全部用现有机制**：git 状态文件 + verify 分支；飞书幂等 = 稳定标识查重 + 唯一性校验 + overwrite（v4 修订，见 3.A）。
4. **交付分工**：git 保留（协调状态 + 运行记录 + 存档），飞书为阅读主渠道，通知走 bot 消息。

## 2. 背景与调研结论

### P1：交付通道与使用场景割裂
GitHub 只做「项目与源码管理」和「核心知识沉淀」，资讯类内容放在飞书，便于阅读与办公软件联动；有价值的信息再择精华沉淀回 GitHub。

### P2：飞书接入能力已验证；但飞书不具备锁能力
2026-11-13 本机全能力实测通过（附录 A.1）；2026-11-14 锁能力实测证伪（附录 A.2）。**飞书能做交付层，不能做锁载体。**

### P3：锁的定位
锁不设计、不改动（定案 2）。依据：单运行者消除并发需求；飞书无锁原语；git non-fast-forward 与现有 start 分流是自然兜底。

### P4：verify 机制是现成的协调手段
`ACTION=verify` 流程依赖「状态文件里已有本周产出」而非锁；替补任务起手的状态分流由现有机制自然完成。

### P5：云端上次失败是凭据未配置（可修复），不是环境不可用
2026-11-12 失败根因是云端无 git PAT（`could not read Username`）。附带发现 `push()` 误分类（本次顺手修复，3.D）。云端能否作为主环境以验收 3 的实测为准。

### P6：代理处理必须自适应，不能统一清除
本机风险：WorkBuddy 工具环境继承的代理变量指向动态端口，观测到死端口（49797 无监听，连接即失败）。
云端事实（Codex 评审修正）：**云环境实际依赖代理与自定义 CA**（SSL_CERT_FILE 等），统一清除会破坏连接。
结论：按「端口是否有监听」自适应处理（3.A），两端各取所需。

### P7：两端飞书同步是同一个实现
同为官方 `@larksuite/cli@1.0.100`，`feishu_sync.py` 两端同一代码路径；差异仅 CLI 位置、凭据初始化、代理环境三处，均被设计收敛（附录 A.6）。

### P8：飞书 user/bot 是两套独立权限（2026-11-15 双端对照实测）
`auth scopes` 的 222 项是 userScopes，**不证明 bot 有同样权限**：应用 bot 建文档在本机与云端同码失败（99991672），bot 发消息成功。方案：建文档走 user，通知走 bot（附录 A.5）。

## 3. 重构清单

### A. 飞书同步（核心新增）

**`scripts/feishu_sync.py`（新增，约 260 行，纯标准库，平台无关）**

```
python3 $S/feishu_sync.py preflight                                # 飞书环境预检（每次运行起手）
python3 $S/feishu_sync.py sync --from-published --sha <sha>        # 常规：同步本次已发布的报告
python3 $S/feishu_sync.py sync --from-published --week 2026-W45    # 补交付：单独重试某周交付
python3 $S/feishu_sync.py notify --file /tmp/ai-weekly/notification.txt
```

**preflight（只查飞书，分级降级）**：
1. lark-cli 不存在 → 写降级模式 `off`；
2. `auth status` 分项：`user` unavailable → 降级 `no_doc`（只跳文档同步）；`bot` not ready → 降级 `no_notify`（只跳通知）；两者叠加 → `off`；
3. 输出 `PREFLIGHT=ok` 或 `PREFLIGHT=degraded:<mode>`，写 `/tmp/ai-weekly/feishu-mode.json` 与 tracelog；
4. **不做 git 检查**：可写性由 `coord.py start` 的现有真实写状态覆盖（评审 #1）；
5. 降级不阻止运行：周报照常生成发布 git，通知按降级形态发出并注明（user 失效→git 链接；bot 失效→平台原样输出）。修复后用 `--from-published` 补交付（评审 #5）。

**sync 流程**：
1. 取同步源：`git show <sha>:<report_path>`（**实际入库内容**，不用 `$OUT_REPORT` 候选稿——它可能被人工修改保护排除，评审 #6）；`--week` 形式缺省取 main 最新；
2. 文档身份：从周报元数据取 ISO 周（如 `2026-W45`）+ 环境（`TEST_RUN` → 测试）。**查重关键词 = `AI 周报 {week}`**（不含「（回溯版）」等可变标记，评审 #2）；文档标题 = 报告 H1（保留标记供阅读区分）；
3. 代理自适应（评审 #4）：对 `HTTP(S)_PROXY` 的 host:port 做 TCP connect（1 秒超时）：通 → 保留（云端真实代理）；不通 → 从子进程环境删除并设 `LARK_CLI_NO_PROXY=1`（本机死端口）；
4. 查重：`docs +search "AI 周报 {week}"`，过滤标题以该串开头的候选——恰 1 个 → `+update --command overwrite`；0 个 → `+create --doc-format markdown`；**>1 个 → 报 `FEISHU_AMBIGUOUS_DOC`，不盲目覆盖**；
5. create 重试：网络类失败重试前**重新执行第 4 步查重**（防响应丢失导致重复建）；权限类失败不重试；
6. 重试 3 次（2/4/8 秒）；耗尽记 `FEISHU_SYNC_FAILED`，不阻塞；
7. 输出 `feishu.json`（document_id、url、action），写 tracelog；document_id 与 url 同时写入通知文本（可读可追溯；git 持久化列入后续，评审 #2 的取舍）。

**notify**：读通知文件 → `im +messages-send --as bot --idempotency-key ai-weekly-{week}-{n}`；失败去全文重发一次；耗尽记 `FEISHU_NOTIFY_FAILED`。

**`config/feishu.yaml`（新增）**：`enabled`、`folder_token`（可空）、`notify.as=bot`、`notify.user_open_id`、`cli_path`（可空=自动探测）。

**两端身份**（不变）：建文档走 user（云端 device 授权一次）；通知走 bot。
