# 提案：飞书接入与定时任务收敛（v3 重构方案）

- 状态：**评审中**（v3.2 提交 Codex 评审，评审后出最终版）
- 提出：2026-11-14
- 关联：版本规划 2026-11 节（待登记）/ 提案《2026-11-11-发布门槛与上线整改》（已实现）
- 演进：v1 初稿 → v2 五点修订（云端为主/飞书锁实测/定性修正）→ v3 定案（锁放弃、备份默认暂停、单运行者）→ v3.1 补调研附录 → v3.2 环境清单与起手预检

## 1. 定案（四条）

1. **单运行者**：云端（Codex）是唯一活跃定时任务（周一 10:00）。WorkBuddy 定时任务**创建即暂停**（PAUSED），仅在云端环境失效（连续失败或服务不可用）时人工启用替补；启用替补前先停云端——**同一时间永远只有一个运行者，无并发**。
2. **锁：不设计、不改动**。现有 `coord.py` 锁代码保留原样——单运行者下自拿自放不构成障碍，且客观上是「误开双任务」时的防呆（第二个运行者会得到 `wait`/`exit`，不会双写），但这只是既有行为的自然结果，**不是本次的设计依赖**。飞书已实测无锁原语（见附录 A.2），不引入任何新锁机制、不加开关。未来若真出现双调度需求，另立提案。
3. **协调与幂等全部用现有机制**：跨周一致性由 git 状态文件（`produced` 字段）+ verify 分支保证；重跑/回溯的飞书幂等由 `feishu_sync.py` 的「标题查重 + overwrite」保证。**零新增协调组件。**
4. **交付分工**：git 保留（协调状态 + 运行记录 + 存档），飞书为阅读主渠道，通知走 bot 消息。

## 2. 背景与调研结论

### P1：交付通道与使用场景割裂

周报只在 GitHub 沉淀，通知全文链接指向 github.com。用户定位已明确：**GitHub 只做「项目与源码管理」和「核心知识沉淀」，资讯类内容放在在线文档（飞书）**，便于阅读与办公软件联动；有价值的信息再择精华沉淀回 GitHub。

### P2：飞书接入能力已验证；但飞书不具备锁能力

2026-11-13 本机全能力实测通过（创建/读回/编辑/通知/并发/凭据，明细见附录 A.1）；2026-11-14 锁能力实测证伪（`--revision-id` 过期写入照样成功，明细见附录 A.2）。**结论：飞书能做交付层，不能做锁载体。**

### P3：锁的定位

用户曾指出「文件锁放在 GitHub 上太重」。v3 定案：锁不设计、不改动（第 1 节第 2 条）。依据：单运行者原则消除了并发需求；飞书无锁原语；git non-fast-forward 与现有 start 分流是自然兜底。

### P4：verify 机制是现成的协调手段

`coord.py start` 输出 `ACTION=verify` 时转校验流程（`verify.py --record`），依赖「状态文件里已有本周产出」而非锁。替补任务启用后，起手状态分流（已完成 → exit / 已有产出 → verify / 无 → run）由现有机制自然完成。

### P5：云端上次失败是凭据未配置（可修复），不是环境不可用

2026-11-12 Codex 云端运行失败（`PUSH_REJECTED`），根因是云端未配置 git 推送凭据（`could not read Username for 'https://github.com'`）。附带发现 `coord.py push()` 把认证错误误分类为 `network`（本次顺手修复，见 3.D）。云端能否作为主环境，以验收第 3 条的实测为准。

### P6：代理变量的真实风险是「死端口连不通」，不是「分流绕路」

实测：Mihomo 规则模式下境内域名（含 open.feishu.cn）经代理也走 DIRECT（附录 A.4）。真实风险：本机 WorkBuddy 工具环境继承的 `HTTP(S)_PROXY` 指向动态端口（观测 49797/52547/50568），其中 49797 实测无监听、连接即失败。防护：同步脚本清理这组变量并设 `LARK_CLI_NO_PROXY=1`。云端无此注入。

### P7：两端飞书同步是同一个实现（2026-11-15 确认）

本机 WorkBuddy 连接器与 Codex 云端安装的是**同一个官方 npm 包 `@larksuite/cli@1.0.100`**（github.com/larksuite/cli，Lark Technologies 版权）。命令、参数、输出结构、包内使用说明（`lark-cli skills read ...`）完全一致。差异仅三处环境项，已被设计收敛（明细见附录 A.6）。

## 3. 重构清单

### A. 飞书同步（核心新增）

**`scripts/feishu_sync.py`（新增，约 180 行，纯标准库，平台无关）**

```
python3 $S/feishu_sync.py preflight                                      # 环境预检（每次运行起手）
python3 $S/feishu_sync.py sync     --report $OUT_REPORT                  # 同步周报到飞书
python3 $S/feishu_sync.py notify   --file /tmp/ai-weekly/notification.txt   # 以 bot 发送通知
```

`preflight` 流程（秒级，不依赖周报产物，失败即停，见 3.B 第 0 步）：
1. 探测 lark-cli（不存在报 `FEISHU_CLI_NOT_FOUND`）；
2. `auth status`：`bot` 须 ready，`user` 须 available（`needs_refresh` 视为 available——会自动刷新）；不满足报 `FEISHU_AUTH_INVALID`，输出里写明修复动作（云端重新 device 授权 / 本机连接器页面重新授权）；
3. `git ls-remote` 探活远端（PAT 失效时在此暴露，报 `GIT_AUTH_INVALID`，比跑到 publish 才失败早约 40 分钟）；
4. 全部通过输出 `PREFLIGHT=ok`，结果写 tracelog。

`sync` 流程：
1. 从 `$OUT_REPORT` 提取一级标题（「（回溯版）」「检查未通过」等标记自动与 git 侧一致）；
2. 探测 lark-cli（`which lark-cli` → WorkBuddy 连接器路径 `~/.workbuddy/binaries/node/cli-connector-packages/bin/lark-cli` → 都没有报 `FEISHU_CLI_NOT_FOUND`）；
3. 子进程环境：删 `HTTP_PROXY/HTTPS_PROXY/http_proxy/https_proxy`，设 `LARK_CLI_NO_PROXY=1`（P6）；
4. `docs +search` 按标题查重：命中 → `+update --command overwrite`（幂等）；未命中 → `+create --doc-format markdown`（`folder_token` 非空时入夹）；
5. 重试 3 次（2/4/8 秒，复用 `runtime.yaml` network 段）；耗尽记 `FEISHU_SYNC_FAILED`，**不阻塞**；
6. 输出 `/tmp/ai-weekly/feishu.json`（`document_id`、`url`、`action=created|updated`），写 tracelog。

`notify` 流程：读通知文件 → `im +messages-send --as bot --user-id <config> --markdown @file --idempotency-key ai-weekly-{week}-{n}`；失败去全文重发一次；耗尽记 `FEISHU_NOTIFY_FAILED`。

**`config/feishu.yaml`（新增）**

```yaml

folder_token: ""            # 可空；建议手动建「AI 周报」文件夹后填入
notify:
  as: bot
  user_open_id: "ou_4ae422ac0cc335fff6212d582972f769"

```

### A.2 飞书锁能力证伪（2026-11-14）

- 现象：`docs +update --revision-id N` 形似乐观锁（base revision）。
- 实验：文档 revision=7 时带 `--revision-id 6`（过期值）append 写入 → 返回 `ok: true`；读回确认过期写入已落盘（`has_bad: true`）。
- 结论：`--revision-id` 只是「基于哪个版本追加」的插入参考，**服务端不做版本冲突检查**。飞书文档为协同编辑设计（最后写入胜出 + 实时合并），docx 与 Base API 均无 If-Match 类条件写；文档内「读标记→写标记」非原子。**飞书不能作为锁载体。**

### A.3 WorkBuddy 连接器形态普查（2026-11-14，486 个官方连接器）

| 形态 | 数量 | 代表 |

| 远程 MCP（`mcp.json` 声明 url：streamable-http / sse） | 393 | 腾讯文档 `https://docs.qq.com/openapi/mcp`、百度网盘 `https://mcp-pan.baidu.com/sse` |
| **CLI 型（无 mcp.json，keywords=[skills,cli]）** | **52** | **飞书、钉钉、腾讯会议、CNB** |

### A.5 身份与凭据机制（含 user/bot 权限边界实测）

- user token 自动刷新：refresh token 有效期内（通常 30 天）有调用即可，每周一跑足够保持活性。

**user / bot 是两套独立权限（2026-11-15 双端对照实测）**：

| 操作 | 身份 | 本机 | 云端 | 结论 |
| --- | --- | --- | --- | --- |
| 创建文档 | user | 成功 | （device 授权后待验） | userScopes 含 `docx:document:create` |
| 创建文档 | bot | **失败 99991672** | **失败 99991672**（同码同文） | 应用未申请 bot 的 docx scope |
| 发消息 | bot | 成功 | 待验（预期成功） | 应用有 bot 的 `im:message` |

要点：`auth scopes` 列出的 222 项是 **userScopes**（`tokenType: user`），**不能证明 bot 拥有同样权限**。bot 建文档报 `app_scope_not_applied`，hint 链接可在开放平台补申请，但 bot 所建文档归应用所有、需再分享给用户——方案因此定为「建文档走 user、发通知走 bot」。两端在同一身份下行为完全一致（同错误码），不存在环境差异。

### A.6 两端同一性与差异（2026-11-15 确认）

同一性：本机连接器与云端 `npm i -g` 同为 `@larksuite/cli@1.0.100`（github.com/larksuite/cli）。命令、参数、JSON 输出结构、包内说明（`lark-cli skills read ...`）一致，**`feishu_sync.py` 两端同一代码路径**。

| 差异项 | 本机 WorkBuddy | 云端 Codex | 收敛方式 |
| --- | --- | --- | --- |
| CLI 位置 | 连接器目录 `~/.workbuddy/binaries/node/cli-connector-packages/bin/lark-cli` | npm 全局 | 脚本自动探测 |
