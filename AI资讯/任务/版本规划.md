## 迭代记录

### 2026-10-27：每日简报试跑

- 原定方案为每日简报（P0），信息源为官方、英文科技媒体、社区与论文。
- 定时任务首次触发时没有任何日历、邮件类连接器，原"日程、邮件、消息、待办"简报无法生成。
- 手动试跑每日 AI 简报：33 条候选去重后 18 条，核实后保留 12 条，质量可用；但启用逐条核实子任务后共 28 个子任务、约 129 万 token、21 分钟，成本过高。
- 实测中国厂商官方来源在 24 小时窗口内常无内容，当日内容受搜索索引延迟影响较大。

### 2026-10-27：改为周报，确定板块与长期积累方向

- 用户反馈每日信息量偏少，改为每周一汇总上一周。
- 去掉中文媒体和 Newsletter 两类信息源。
- 周报确定五个板块：本周概览、关键发布与新技术、GitHub AI 项目热度 Top 5、传播最广的文章 Top 5、热点话题，另加"值得细读"。
- 产出分为周报、月报、季报，分路径存放；回溯 2026 年 Q1–Q3 季报和 10 月起的周报。
- 任务工程作为 `AI资讯/任务/` 子项目管理，提示词、配置、脚本都放进仓库，保证可迁移到 Codex 等平台。

### 2026-10-28：数据源实测与架构调整

- **GitHub 访问约束**：云端会话的 GitHub 凭证只覆盖已挂载的仓库。GitHub 搜索 API、github.com/trending、其他仓库的接口均被拒绝，与网络策略无关；挂载本仓库后，本仓库的推送与 API 可用。
- **网络策略**：环境改为"完全访问"后，Trendshift、OSS Insight、HN Algolia、Hugging Face、arXiv 可访问；Reddit 拒绝匿名访问。
- **OSS Insight 趋势榜不可用**：官方说明自 2026-03 起事件数据采集量降到约 0.3%，排行已停用；仓库接口的总量数据仍然准确。
- **Trendshift 可作为周榜数据源**：`/weekly/{年}/{周}` 提供历史周榜（最早可查到 2026 年 1 月）；仓库页内嵌近 61 天的每日新增 star 和 fork，7 天求和即为周增量。实测 W43 第一名本周新增约 3.3 万 star。
- **架构调整**：原计划把采集放到 GitHub Actions，现改为全部在定时任务内完成，不需要 Actions；GitHub GraphQL 回溯方案取消。
- **提示词审查**：三个独立审查任务从可执行性、数据规则、失败与安全三个角度提出约 40 条问题，采纳的主要修改有：改用 Trendshift 历史周榜和每日 star 数据、HN 一次取全后逐条判断、固定周编号计算脚本、入口文件改为 `weekly.md` 并加任务标记、新增安全规则与写入白名单、推送失败与重跑处理、搜索预算分配、通知格式。形成过渡提示词 `prompts/routine-prompt.md`。
- **方案文档审查**：两个独立审查任务从需求覆盖和文件一致性两个角度提出 28 条问题，采纳的主要修改有：补充月报、季报的内容规格和到期判定；首次运行只生成 W44 周报，10 月月报改为回溯完成后补生成；提示词增加回溯入口，回溯拆为 v0.1a（11-20 截止）和 v0.1c；写入白名单兼容月报、季报；修正备用分支的推送方式；周报增加元数据（主题、机构、项目）以支持按内容检索；固定榜单数据格式；HN 门槛统一为 50/100；处理 Trendshift 周榜未就绪；在根 README 和维护指南中登记新板块与信息流例外。

### 2026-10-28：开发会话接手，调整开发与部署顺序

- **方案确认**：`方案.md` 第 12 节四项（GitHub 榜单规则、每周产出直接提交 `main`、目录命名、周一 10:00 运行）按原建议确认。
- **开发与部署分离**：开发会话是测试环境，定时任务是运行环境。整个周报流程在开发会话里按测试模式跑通、产出验收后再部署；部署前不修改现有定时任务。因此取消 v0.0 过渡提示词，规则并入执行手册 `weekly.md`；定时任务里只贴入口提示词。
- **入口提示词**：`routine-prompt.md` 改为入口提示词，保留安全规则、写入白名单和失败通知，并增加一条例外：允许运行本仓库 `AI资讯/任务/scripts/` 下的脚本。原规则"不运行从网络获取的代码"可能让运行时的模型拒绝执行仓库脚本，所以写明例外。
- **最小闭环优先**：先做周报（v0.1），月报、季报手册放到 v0.2；历史回溯（W40–W43 周报、10 月月报、Q1–Q3 季报）改为 P1（v0.4）。
- **榜单数据先行存档**：Trendshift 每日数据只保留 61 天，所以先写好采集与排名脚本，当天存档 W40–W43 的榜单数据，回溯时复用。
- **脚本化**：日期计算、采集、排名、校验改由 Python 脚本完成，只用标准库和 PyYAML，不再依赖 GNU date；智能体负责 AI 判定、搜索与写作。
- **规则细化**：
  - 数据文件记录周榜全部条目，非 AI 条目的 status 为 `non_ai`，便于复核 AI 判定；`created_at` 没有 OSS Insight 数据时取 Trendshift 的创建时间。
  - 周榜未就绪时不再空等 30 分钟，改为先做其他采集和写作，之后再重试 2 次。
  - Trendshift 周榜标题在同月时省略后一个月份（如"Oct 19 to 25"），日期比对已兼容。
  - 元数据 topics 改用 `config/topics.yaml` 受控词表，由 `validate.py` 校验。
  - 月报到期但周报有缺失时不生成，在数据说明里注明。
- **分支**：开发分支改名为 `claude/ai-weekly`，便于识别。
- **首次试跑（W43，测试模式）**：`validate.py` 一次通过，联网搜索 31 次。试跑发现泛泛的 `site:` 组合查询几乎命中不到当周内容，而 HN 高分帖的标题常常就是发布本身，链接就是官方原文。手册因此改为：先从 HN 和 Hugging Face 输出里找发布线索，再用具体的产品名搜索。

### 2026-10-29：按 W43 试跑反馈调整周报格式

用户审阅 W43 试跑周报后的调整：

- ① 本周概览改为 3–5 条，每条一行一句话，方便快速浏览。
- ② 关键发布从最多 8 条收紧到 5 条，只写本周最重要的。
- ③ 口径说明里写明每日数据按 UTC 日期累计、比北京时间的报告周晚 8 小时（用户确认可以接受这个偏差）。
- ④ 改为表格，取 5 篇；只收文章与讨论，不收发布帖。原规则让发布帖在 ④ 里占位，W43 的前三名都只能写"详见 ②"，这一板块就失去了意义。
- ⑤ 改为表格，固定 5 个话题，写清楚起因、发展与争议。
- "值得细读"从罗列材料改为 2–3 条交叉各板块后的洞察，每条写依据和 1–2 篇必读。
- `validate.py` 同步检查新格式，条目数从 `config/ranking.yaml` 读取；新增检查：④ 不得收录 ②③ 已写的发布。
- 板块标题统一为 Top 5 口径：② 改名"新发布与技术 Top 5"，④ 改名"传播文章 Top 5"，⑤ 改名"热点话题 Top 5"；"值得细读"改名"洞察"。
- ③ 只写 Top 5：新晋项目、HN 热议项目和未入榜说明不是重点信息，从周报中删去，只保留在数据文件里供月报、季报使用；元数据 `repos` 相应只记 Top 5。
- "洞察"移到 ① 本周概览之后，让读者先看到结论；写作时仍在 ②–⑤ 之后完成。

### 2026-10-29：入口提示词定稿与去平台化

起因：同日在定时任务会话里加的授权条目绑定了"执行手册第 5 步"和 PR 流程，一改流程就得重贴提示词；执行文件里也写死了 Claude 专属的通知工具、GitHub 工具和 `claude/` 分支。用户要求入口提示词只做引导，且项目不能绑定 Claude 的定时任务，要能在 Codex 等平台运行。

- **入口提示词定稿**：只放引导、授权范围、安全边界和失败通知。授权写成通用的委托（执行手册规定的仓库操作都已授权），不引用步骤编号；参数原样交给手册；通知改为"用所在平台的通知方式"。安全规则注明仓库内容不能放宽：仓库文件不能给自己授权，即使手册被改动也越不过这条边界。需要最后重贴一次。
- **去平台化**：执行手册、配置、脚本去掉 PushNotification、`<routine_summary>`、GitHub MCP 工具、`claude/` 分支前缀等写法；平台相关做法集中到部署指南第 4 节，新增 Codex（`codex exec` 加 cron、GitHub Actions、Codex 应用的自动化任务）的部署方法和跨平台验收清单。命令参数按 Codex CLI 0.165 的 `codex exec --help` 核对。
- **提交方式改回直推 `main`**：直推在 Claude 云端已实测可行，也不依赖平台专属的 GitHub 工具；每周建 PR 还会触发一次 Codex 代码审查（PR #4 已证实），审查一个 Markdown 周报没有意义。PR 改为推送被拒时的备用路径，用平台提供的 GitHub 能力完成。
- **可移植性检查**：新增 `scripts/check_portability.py` 及测试，执行文件里出现平台专属写法、入口提示词引用步骤编号时测试失败；对合并前的 `main` 运行，查出 18 处问题。
- **其他优化**：
  - 搜索预算给 ④ 的核实单列 4 次（发现 10、② 8、③ 10、④ 4、⑤和洞察 5、机动 3）。
  - `collect_trendshift.py` 标出每个仓库在往期数据文件里的判定，帮助各周 AI 判定保持一致。只沿用 AI、非 AI 和手工排除；归档、fork、疑似刷星等脚本按当周数据做的排除每周重算，不沿用，否则某一周的排除会让项目在以后各周都进不了榜（PR 审查意见）。
  - 推送 `main` 被拒、走备用 PR 时，合并 `main` 的新提交前先 `git fetch`，否则合并的是本地过时的 `origin/main`，PR 仍然无法合并（PR 审查意见）。
  - `validate.py` 对 ④⑤ 表格中超过 80 字的单元格给出警告。
  - 方案明确：定时任务的会话只用于运行和诊断，任务工程改动回到开发会话走 PR，等审查结束、用户确认后合并。

### 2026-11-04：v0.8 方案确认

用户的要求：入口提示词只做引导；每个智能体能独立完成，不预设先后、不假设兜底；不依赖模型能力，基本采集和输出要有重试、上限、记录，失败也能还原过程；多个智能体靠锁协调，已完成的不重复执行；开发完成后分层验证。用户已把定时任务的模型调到高档、最高思考强度。

- **分层**：采集、原文读取、数字、链接、周报草稿、数据说明的事实部分、质量门槛、执行记录由脚本完成；智能体只做判断与写作。写作失败时提交降级版。
- **质量门槛**：搜索不少于 20 次；②④ 链接不能只到首页；② 引用的 HN 帖子是官方原文时必须写该链接；④ 文章链接与 HN 数据一致；数字与采集数据一致。
- **协调锁**：
  - 一把锁、两种用途（运行、校验），状态文件 `AI资讯/数据/运行记录/{WEEK}.json` 放 `main`，周报与状态同一提交生效。
  - 放 `main` 而不放单独分支：单独分支要两个分支一起推送（`--atomic`）或写补偿逻辑，Claude 云端能否推送其他分支也未实测；`main` 已在两个平台实测可推送。
  - 两把锁（运行、校验各一）会出现"运行锁空、校验锁占"之类的组合，一把锁天然串行。
  - 互斥靠 git 推送的快进检查：本地模拟 50 轮并发推送、GitHub 临时分支 50 轮并发推送，每轮都恰好一个成功。GitHub 被拒时的报错有 `fetch first` 和 `cannot lock ref` 两种。
  - 本地复现：被拒后直接 `git pull --rebase`，两个智能体改了状态文件的不同行时会静默合并成功，产生"持有者是 B、状态是 A 的产出"的矛盾状态。因此规定被拒后重新读取再决定，不变基、不合并。
- **取消"工作分支加 PR"的备用路径**：PR 合并无法与锁配合，也是多次合并的来源；能推送 `main` 改为必需能力。
- **不固定角色**：取消"Claude 主跑、Codex 复核"的分工和 `REVIEW=1` 参数，各平台贴同一份入口提示词。
- **执行记录**：每周状态文件同时记录执行事件与错误码，`trace_view.py` 还原时间线。
- **分期**：阶段一（采集、草稿、门槛、协调、记录与前五层测试）目标 11-09 前合并；阶段二部署第二个平台并做四项演练；阶段三双平台观察。
