# 部署指南

> 本文说明如何验收 AI 资讯任务，并把它部署到定时运行平台。部署所需的参数集中在 `config/task.yaml`，本文按平台说明怎么配置。

## 1. 设计原则：不绑定平台

- **入口提示词**（`prompts/routine-prompt.md`）是贴进定时任务的唯一内容，只放四类东西：引导去读执行手册、授权范围、安全边界、失败通知。它不写具体步骤，也不写平台专属的工具名，所以换平台、改流程都不用改它。
- **执行手册、模板、配置、脚本**只写平台无关的步骤：shell、git、python3、联网搜索，加上"用所在平台的通知方式""用平台提供的 GitHub 能力"这类说法。
- **平台相关的做法**（定时、通知、GitHub 操作、沙箱与网络）只写在本文第 4 节。
- `scripts/check_portability.py` 检查以上约定：执行文件里不能出现平台专属的写法，入口提示词不能引用手册的步骤编号。它随单元测试自动运行。

## 2. 部署前提

| 能力 | 用途 | 必需 |
| --- | --- | --- |
| 定时触发 | 每周一 10:00（Asia/Shanghai）运行 | 是 |
| Shell、git | 执行脚本、提交、推送 | 是 |
| python3（带 PyYAML） | 运行 `scripts/` 下的采集、排名、校验脚本 | 是 |
| 命令可以联网 | 脚本访问 `config/task.yaml` 的 `network.allow` 中的站点；git 推送 | 是 |
| 联网搜索 | 官方发布、媒体报道、传播分析 | 是 |
| 推送本仓库 `main` 的凭证 | 周报和数据文件直接推送到 `main` | 是 |
| 建 PR 并合并 | 推送 `main` 被拒时的备用路径 | 否 |
| 发送通知 | 把周报精简版推送给用户；没有时把通知作为运行的最后输出，由调度方转发 | 否 |

模型选择平台上的中档通用模型即可。仓库文件中不写具体型号，在平台设置中选择。

## 3. 部署前验收（开发会话）

开发会话是测试环境，定时任务是运行环境。任务工程有改动时，先在开发会话里完整跑一遍，产出确认符合预期后再部署：

1. 运行单元测试（含可移植性检查）：`python3 -m unittest discover -s AI资讯/任务/scripts/tests -t AI资讯/任务/scripts/tests`。
2. 按入口提示词和执行手册运行一次，参数加 `TEST_RUN=1`；要测指定的周，再加 `TARGET_WEEK=YYYY-Www`。测试模式不推送、不发通知，周报和数据文件提交到当前分支，通知内容在最后输出。
3. 审阅周报、数据文件和通知内容，按反馈调整规则后重跑。
4. 走 PR，等审查结束后合并；然后按第 4 节部署或更新定时任务。

定时任务的会话只用于运行和诊断。要改任务工程，回到开发会话走 PR，不在定时任务里直接改。

## 4. 平台适配

### 4.1 能力对应

| 能力 | Claude Code 云端定时任务 | Codex | 自建调度（cron 或 CI + 任意智能体 CLI） |
| --- | --- | --- | --- |
| 定时 | 定时任务设置周一 10:00（GMT+8） | Codex 应用的自动化任务；或 cron / GitHub Actions 调用 `codex exec` | `CRON_TZ=Asia/Shanghai` 下的 `0 10 * * 1`，或 UTC 的 `0 2 * * 1` |
| 运行入口提示词 | 定时任务的提示词框 | `codex exec`，提示词从标准输入读取 | 智能体 CLI 的非交互模式 |
| 联网搜索 | 内置 | 加 `--search`（实时搜索；不加时用缓存索引） | 平台内置搜索或搜索 API |
| 命令联网 | 环境网络设为"完全访问" | 沙箱默认不联网：`-s workspace-write -c sandbox_workspace_write.network_access=true` | 运行环境放行 `network.allow` 中的站点 |
| 推送凭证 | 定时任务挂载本仓库后由平台注入 | 运行环境里的 git 凭证 | 只对本仓库有内容写权限的细粒度 token 或部署密钥 |
| 推送 `main` | 2026-10-29 实测可以直接推送 | 有凭证即可 | 有凭证即可 |
| 备用的建 PR 与合并 | 平台的 GitHub 工具；平台会指定一个 `claude/` 开头的工作分支 | `gh pr create`、`gh pr merge --merge`（需要 `GH_TOKEN`） | 同左 |
| 通知 | PushNotification，内容放在 `<routine_summary>` 标签里，首句作为横幅 | 没有内置推送：用 `-o <文件>` 保存最后一条消息，由调度脚本转发 | 由调度脚本转发最后输出（邮件、IM 机器人等，待定，见版本规划"多渠道每周通知"） |

### 4.2 Claude Code 云端定时任务（当前平台）

1. **环境**：定时任务使用的云端环境，网络访问设为"完全访问"，或在白名单中加入 `config/task.yaml` 列出的域名。环境可能被多个会话共用，修改会影响所有使用它的任务。
2. **GitHub 授权**：在"连接器 → GitHub 集成"中连接 GitHub 账户并安装 Claude GitHub 应用；在定时任务的编辑页把本仓库加入仓库列表。仓库在会话启动时挂载，运行中不会补加。
3. **定时任务配置**：

| 项目 | 设置 |
| --- | --- |
| 运行时间 | 每周一 10:00，时区 GMT+8 |
| 模型 | 中档通用模型 |
| 仓库 | slamslammo/personal_knowledge_manager |
| 提示词 | 复制 `prompts/routine-prompt.md` 全文 |

执行手册、脚本和配置合并到 `main` 后，下一次运行即生效；只有 `routine-prompt.md` 本身变化时才需要重新粘贴。

### 4.3 Codex

Codex 部署用于验证本任务不绑定 Claude，也可以作为正式运行的平台。以下命令按 Codex CLI 0.165 的 `codex exec --help` 核对过；GitHub Actions 与 Codex 应用的自动化任务以 OpenAI 官方文档为准，本项目尚未实测。

**方式 A：cron 加 `codex exec`（本机或服务器）**

1. 克隆本仓库，配置只对本仓库有写权限的 git 凭证，登录 Codex CLI，安装 python3 与 PyYAML。
2. 测试模式先跑一次（在仓库根目录）：

   ```bash
   { echo "TEST_RUN=1"; echo; cat AI资讯/任务/prompts/routine-prompt.md; } \
     | codex exec --search -s workspace-write \
         -c sandbox_workspace_write.network_access=true \
         -o /tmp/ai-weekly-last.txt -
   ```

3. 正式运行时去掉第一行的 `TEST_RUN=1`，放进 crontab：

   ```bash
   CRON_TZ=Asia/Shanghai
   0 10 * * 1  cd /path/to/personal_knowledge_manager && codex exec --search -s workspace-write -c sandbox_workspace_write.network_access=true -o /tmp/ai-weekly-last.txt - < AI资讯/任务/prompts/routine-prompt.md
   ```

4. 通知：Codex 没有推送到手机的功能，`/tmp/ai-weekly-last.txt` 里是最后一条消息（含通知内容），由 cron 脚本转发，转发渠道待"多渠道每周通知"确定。

**方式 B：GitHub Actions**：用 `on: schedule`（cron `0 2 * * 1`，即北京时间周一 10:00）触发 `openai/codex-action@v1`，提示词用 `routine-prompt.md` 全文。需要仓库 secret `OPENAI_API_KEY`，任务的 `permissions` 要有 `contents: write` 才能推送 `main`。

**方式 C：Codex 应用的自动化任务**：按官方文档设置每周一 10:00 运行，提示词贴 `routine-prompt.md` 全文，并确认运行环境允许命令联网和推送。

### 4.4 跨平台验收清单

新平台首次部署时逐项检查，结果记入 `版本规划.md`：

- [ ] 测试模式（`TEST_RUN=1`）跑通：周报生成，`validate.py` 与 `check_run.py` 都通过，通知内容出现在最后输出里。
- [ ] 正式运行一次：周报和数据文件进入 `main`（直接推送，或经备用 PR 合并），`git log` 里的提交信息为"AI 周报 {WEEK}"。
- [ ] 通知送达；平台没有通知能力时，最后输出能被调度脚本取到。
- [ ] 与其他平台同一周的产出对照：GitHub Top 5 的名次与 star 数应一致（由脚本决定）；②④⑤ 的选题可以不同，但都要满足模板和校验规则。
- [ ] 期间没有需要人工点"确认"的环节；如有，说明该平台的授权或沙箱配置还不够。

### 4.5 上线检查（每个平台正式启用前）

手动触发一次正式运行，检查：

- [ ] 周报文件生成在 `AI资讯/周报/{ISO 周年}/{WEEK}.md`，开头有元数据
- [ ] 数据文件生成在 `AI资讯/数据/github-weekly/{WEEK}.json`
- [ ] 提交出现在 `main`；如果走了备用 PR，PR 已合并
- [ ] 收到通知，首句格式为"【AI周报 W..】……"，全文链接可以打开
- [ ] 通知的"运行结果"三行显示校验通过、第 0–4 步全部完成、已进入 `main`

## 5. 回溯运行

在提示词前加一行 `TARGET_START=YYYY-MM-DD`（目标周的周一）或 `TARGET_WEEK=YYYY-Www`，即按回溯模式生成该周周报。榜单数据文件已存在时直接复用；不存在且已超出 Trendshift 每日数据的 61 天窗口时，③ 无法精确计算本周增量，要在数据说明中注明。

## 6. 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 推送报 403，提示仓库不在授权列表 | 运行环境没有本仓库的写权限（Claude 云端：定时任务没有挂载本仓库） | 配置推送凭证；Claude 云端在定时任务编辑页挂载仓库 |
| 通知首句标明"未合并" | 推送 `main` 被拒，备用的 PR 也没能合并 | 按通知里的分支名手动合并；检查凭证或 GitHub 应用的仓库权限 |
| 通知首句标明"检查未通过" | `check_run.py` 发现有步骤没做完，或 `validate.py` 仍有错误 | 看周报数据说明里的剩余问题；必要时手动触发重跑 |
| 脚本报网络错误、`git push` 连不上 | 运行环境禁止命令联网（Codex 沙箱默认如此） | Codex 加 `-c sandbox_workspace_write.network_access=true`；其他平台放行 `network.allow` 中的站点 |
| `git commit` 报只读或 Operation not permitted | 部分沙箱默认保护 `.git` 目录 | 按平台文档放开 `.git` 的写权限；在已隔离的运行环境里，也可以改用 Codex 的 `-s danger-full-access` |
| 脚本报 TLS 或代理错误 | 环境网络策略拦截，或代理证书未配置 | 检查环境网络设置是否放行了这些站点 |
| api.github.com 返回 403 | 部分托管环境只允许访问指定仓库的接口 | 不使用 GitHub 搜索和 Trending，榜单统一用 Trendshift |
| OSS Insight 请求超时 | 接口偶发挂起 | `rank_github.py` 会重试；仍失败的仓库在数据文件 note 和数据说明中注明 |
| `collect_trendshift.py` 退出码 3 | 周榜尚未生成（307、空列表或日期不符） | 手册已安排在其他步骤之后重试；连续出现时考虑推迟运行时间 |
| Trendshift 解析不到 ItemList 或每日数据 | 页面结构变化 | 在数据说明中记录，修订 `collect_trendshift.py` 的解析规则并补测试 |
| `validate.py` 报错 | 周报结构、元数据或与数据文件不一致 | 按报错修改；规则本身需要调整时，同步修改模板、`validate.py` 和测试 |
| `check_run.py` 报"未完成" | 某一步没有在本次运行中做（跳过采集、没重新排名、没记录搜索、没重写周报） | 回到那一步补做，不要只改周报文字 |
| `check_portability.py` 报问题 | 执行文件里写进了平台专属的写法，或入口提示词引用了手册步骤编号 | 把平台相关的内容挪到本文第 4 节，执行文件里改成平台无关的说法 |
