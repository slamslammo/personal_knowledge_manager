# 部署指南

本文说明项目的云端验收、正式启用与备份切换。具体运行步骤在 `prompts/weekly.md`，初始化在 `prompts/env-bootstrap.md`，部署模式在 `config/deployment.yaml`。当前目标是 **Codex 云端唯一运行者，WorkBuddy 本机备份暂停**。

## 1. 设计原则

- 定时任务仅保存一份稳定入口 `prompts/routine-prompt.md`：指向项目、授予必要执行权限、规定安全边界和失败报告。部署版本、命令、验收流程与模式切换由项目维护，不为每次测试临时改任务提示词。
- 本次入口修订只处理旧的“禁止安装、GET-only、禁止初始化配置”等授权冲突。最终入口一次同步到平台后，后续项目流程更新随 `main` 生效；只有用户改变长期授权边界时才需要再次调整入口。
- Git 是生产交付基础；飞书是可降级交付层。Python/PyYAML、Git 写入失败才阻断 Git 周报；飞书 CLI、user、bot 或网络失败只降级文档或通知，环境重验也不能恢复“飞书失败整周停产”。
- `ENV=ok` 只证明核心依赖就绪。`DELIVERY=ok` 只证明本次机器交付检查通过。沙箱结果、正文核对、bot 实际送达、跨任务凭据与刷新均分项验收，不能以就绪标记代替。
- 当前单运行者策略优先于历史多平台方案。协调脚本仍用于状态、提交和恢复，但 Git 发布后释放的锁不覆盖后续飞书同步；不能仅靠错开时间启用两端。

## 2. 部署前提

| 能力 | 用途 | 是否阻断 Git 周报 |
| --- | --- | --- |
| Shell、Python ≥3.10、PyYAML、git | 生成、校验、协调发布 | 是 |
| 本仓库写入身份、命令联网 | 正式 Git 推送；早期 dry-run 为初筛 | 是 |
| 联网搜索及数据来源可达 | 采集与质量门槛 | 按执行手册处理来源降级 |
| Node ≥18、lark-cli | 飞书交付 | 否 |
| 飞书 user / bot | user 文档、bot 通知 | 否，分别降级 |
| 可回写的跨任务凭据保存机制 | 独立定时任务免扫码、刷新后继续使用 | 是长期飞书无人值守验收条件，不阻止 Git 降级生产 |

复用平台已有 GitHub 写入授权；不足时由用户在安全设置提供仅本仓库写权限的身份。细粒度 token、平台仓库授权均可，不强制新建 classic `repo` PAT。任何密钥都不要发到聊天、写进仓库或输出到报告。

网络保留平台原有代理和 CA。允许依赖源、GitHub 及必要发行下载主机、飞书官方鉴权/文档端点，以及采集所需来源；网络访问权限和服务身份权限分别验证。

## 3. 开发验证与项目开关

1. 在开发工作区运行 `python3 -m unittest discover -s AI资讯/任务/scripts/tests -t AI资讯/任务/scripts/tests`，以及 `python3 AI资讯/任务/scripts/check_portability.py`。
2. `config/deployment.yaml` 当前为 `mode: acceptance`。同一份固定入口即可完整试跑，无需向定时任务提示词加 `TEST_RUN` 或目标周参数。
3. 验收模式通过 `deployment.py start` 自动使用本地裸仓库，真实执行协调、提交和推送；不会向 GitHub 发布本轮报告。飞书只匹配/更新 `[测试]` 文档，真实通知跳过。
4. `deployment.py finish` 核对本轮真实产物并报告本次验收结果。它不会自动批准上线、切换配置或启用调度。
5. 工程修改在开发流程中审阅提交。运行任务不得修改提示词、脚本或部署配置。证据通过后由用户明确批准，将项目开关改为 `production`；定时任务保存提示词不变。

### 4.2 其他平台与历史方案

此前 Claude Code 云端及多平台并行是历史方案，当前不作为同时启用的主任务。以后换平台时复用同一项目入口，并先按 4.9 的 C.4 排空旧端。

cron、GitHub Actions、Codex CLI 都是其他部署方式，不是本轮 Codex 云端定时任务的前提。无需在云任务中另装一层 Codex CLI 或建立系统 cron。平台自身的定时任务结果和通知功能以平台当前实际能力为准，不套用旧 CLI 的“没有手机通知”结论。

### 4.3 Codex 云端真实验收步骤

1. **准备可复用云环境。** 在环境设置选择或编辑 `personal_knowledge_manager`，确认仓库 `main`、联网、依赖安装权限和 Git 写入身份。发布准备好的环境。修改当前会话不等于修改后续任务来源，发布快照也不等于可回写的共享凭据存储。
2. **更新既有任务一次。** 在 Scheduled/定时任务找到“AI每周简讯”，先保持暂停；将最终 `routine-prompt.md` 全文同步进去，确认使用上述已发布云环境。若显示继承，核对源会话绑定；不能把未返回环境详情解释成已确认绑定。不要重复创建同用途任务。
3. **保持项目验收模式。** 确认 GitHub `main` 中 `config/deployment.yaml` 是 `acceptance`。不要向保存提示词添加测试参数。WorkBuddy 保持暂停。
4. **立即运行。** 若 Run now 只对启用任务可用，先短暂启用，再点击立即运行；每轮结束后暂停，防止验收尚未完成就进入长期周期。记录运行链接、实际代码提交号和环境来源。
5. **按项目报告补人工项。** 程序自动安装授权范围内的缺项、检查配置；需要本人浏览器飞书授权或平台身份设置时，由本人完成。无人值守任务可以报告缺项后结束，不依赖它无限等待浏览器确认。完成后再次“立即运行”，固定入口不改。
6. **核对沙箱结果。** 应有完整生成和检查、本地沙箱提交号、`[测试]` 飞书文档链接及正文核对、`NOTIFY=skipped`。飞书降级时允许 Git 沙箱完成，但本次完整交付验收仍是 pending/failed。`deployment.py finish` 不能以 skipped 或未完成项冒充通过。
7. **独立任务验证 C9。** 从同一已发布配置启动后续独立运行，检查免扫码读取、此前观察状态是否存在；自然到期后首次 API 调用刷新成功；再由后续独立运行验证新状态被继承。保存各运行记录。若平台没有可回写状态机制，报告阻塞项并保持验收模式，不能只复制一份旧快照或重复本机进程来宣称通过。
8. **正式启用。** 用户审阅本次沙箱、正文及 C9 证据后明确批准，将项目配置改为 `production` 并发布到 `main`，用于一次正式手动验收。立即运行后先暂停，确认真实 Git 提交、飞书同步和 bot 实际通知到达；这些也通过后，再保持每周一 10:00 的唯一主任务启用，复核一次真实定时触发。任务提示词不再改。

手动触发证明执行入口可运行；一次真正的定时触发才证明调度按时启动。云端定时任务的每次运行是否重用实例、是否提供持久存储，均以平台实际配置与跨任务观察为准。

### 4.4 本次沙箱判据

- [ ] 运行记录包含实际提交版本、环境来源、本次计划为 acceptance。
- [ ] `check_run.py` 完整性和质量检查通过；沙箱真实发布，生产 main 不产生本轮报告提交。
- [ ] 飞书文档标题带 `[测试]`，正文与本轮沙箱发布内容一致；保留文档作证据。
- [ ] `NOTIFY=skipped`，通知文本在最后输出。跳过不等于 bot 送达已验收。
- [ ] `deployment.py finish` 报告本次结果，并列出未覆盖项；没有自动切生产或启用调度。

### 4.5 正式运行判据

- [ ] 周报、榜单数据和运行状态进入 main，链接与提交号可核对。
- [ ] `trace_view.py --week {WEEK}` 能看到完整时间线；质量与完整性结论与真实检查一致。
- [ ] 飞书正文来自已发布提交；bot 通知实际收到且链接可打开。
- [ ] 凭据跨任务、自然到期刷新及刷新状态继承分别有证据。
- [ ] 首次配置后不需人工审批即可运行；再观察一次真正定时触发。

### 4.6 单运行者约束

历史协调功能仍保留，当前不按“各端错开一小时就同时启用”运行。Git 发布后还有飞书同步在途，切换时必须停止调度、排队及重试，并确认旧任务与同步子进程结束。具体规程见 C.4。

### 4.7 WorkBuddy 本机备份（默认暂停）

备份仅在云端退出并排空后启用。本机须开机并登录，连接器需有效；备份的存在不能替代云端 C9 验收。恢复云端时先停备份并排空，任何时刻仅一个运行者。

### 4.8 飞书同步、通知与补交付

- `feishu_sync.py preflight` 的普通状态用于分级降级，不等于实际网络或服务端验证。user 失效为 no_doc，bot 失效为 no_notify，双缺为 off；不阻 Git 生产。
- `sync --from-published --sha <sha>` 使用已发布提交内容。文档显式 user，通知显式 bot。标题按栏目和完整 ISO 周匹配，遍历分页后判唯一，多候选拒绝覆盖。
- create 网络失败不盲目重建；覆盖更新可幂等重试。新建结果不明时保留 unknown，人工核查后再补交付。
- 测试隔离认项目部署模式、`coord.json` 的 test 标记与显式测试环境变量，任一为真即测试；部署配置缺失或非法时交付脚本也按测试保护。验收 start 自动建立协调沙箱标记，文档标题带 `[测试]`，notify 脚本直接跳过，包括尚未启动协调时的失败通知。
- 飞书故障修复后使用 `sync --from-published --week <W>` 补同步，不重跑整周；必要时补通知。网络不明的通知使用同一幂等键重试，不换键盲目双发。
- 保留云端有效代理与 CA；脚本仅处理连续探测无监听的回环代理变量，不统一清空。

| C4 | 应用绑定 | 当前激活 appId 为 `cli_a92390bc96f9dbb4`，应用“小龙虾1号” | 精确核对当前身份 |
| C5 | bot 通知 | 服务端身份验证、单独记录实际送达证据 | 验收模式 skipped 不算送达 |

| C9 | 跨任务凭据与刷新 | 平台实际安全保存机制覆盖配置、加密主密钥与 DPoP；独立任务免扫码、到期 API 刷新、再由后续任务继承新状态 | 分项记录，不能以发布快照或同实例重跑替代 |

C9 观察使用 `credential_probe.py --resume`（有旧记录就实际读取）或 `--doc <测试文档ID>`。状态默认 `~/.local/state/ai-weekly/`，可配置 `AI_WEEKLY_STATE_DIR`；记录仅含脱敏标识、过期时间和实例观察，**不保存/搬运凭据**。脚本的实例线索必须结合平台任务记录，不自动证明存储机制正确。第一次成功、同实例重跑、新实例读取和到期刷新要分开报告。

已观察到 refresh token 期限约 7 天；每周跑一次没有可靠延迟余量。必须按实际返回期限落实提前保活和刷新后回写，不承诺“每周运行就足够”。

**C.2 本机四项**：连接器授权、user 文档读写、bot 通知、代理与网络均按实际结果记录；本机结果不能替代云端独立任务验收。

**C.3 启用判据**：核心就绪 → 本次沙箱完成 → 文档正文核对 → C9 分项实测 → 用户批准项目 production → 正式手动运行并验证 bot 送达 → 长期启用并核验真正定时触发。测试开关和结果在项目维护，不临时改任务入口。

**C.4 备份启停规程**

- 启用备份：停云端调度、排队与重试 → 确认旧任务和 lark-cli 子进程均已结束、在途同步完成或终止 → 启用 WorkBuddy 备份。
- 恢复云端：停备份调度、排队与重试 → 确认无在途实例和同步 → 恢复云端唯一运行者。

### 4.10 核心就绪标记与验收状态

`env_check.py ensure` 缓存的是核心依赖状态 `core_ready`，不是生产验收。版本更新触发重查；快路径仍检查核心可执行依赖，Git 写入由真正协调操作证明。飞书交付动态状态不借核心标记维持“永久可用”。

`env_check.py check` 输出核心状态及交付缺项；`check --require-delivery` 用于初始化阶段的严格机器检查。人工验收项单独为 pending，不因为退出码 0 或标记存在而自动通过。

初始化由 `weekly.md` 自动引导，无需另向任务粘贴部署提示词：自动处理授权范围内的依赖和配置，人工项报告后由用户在安全设置或浏览器完成，再触发运行。项目保持 acceptance，直到用户批准正式切换。

## 5. 回溯运行

开发或一次性回溯会话可显式传 `TARGET_START=YYYY-MM-DD` 或 `TARGET_WEEK=YYYY-Www`，不为回溯修改生产定时任务保存提示词。目标周由 `weeks.py` 解析；榜单数据可复用，缺历史数据时按手册注明局限。部署模式仍决定本地沙箱或正式远端，回溯不能绕过隔离。

## 6. 故障排查

先看执行记录：`python3 AI资讯/任务/scripts/trace_view.py --week {WEEK} --errors`。错误码的含义：`python3 AI资讯/任务/scripts/tracelog.py codes`。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `coord.py` 报 `PUSH_DENIED` | 运行环境没有推送 `main` 的权限 | 核对所选云环境、仓库写入身份和分支策略 |
| `coord.py` 报 `STATE_INVALID` | 状态文件被手工改坏 | 人工修复或删除该周的状态文件（走 PR），再手动触发 |
| 通知首句标"需人工" | 本周 3 次产出尝试都没通过 | 看 `trace_view.py` 找原因；修复后删除该周状态文件重跑，或手工补写 |
| 通知首句标"未提交"（`ACTION=lost`） | 运行太久，租约过期后被其他运行接管 | 一般不用处理，接管方会完成；频繁出现时调大 `runtime.yaml` 的租约 |
| 通知首句标"检查未通过" | 质量门槛改了 3 轮仍未通过 | 看数据说明和执行记录里的错误码；必要时手动触发重跑 |
| 通知首句标"降级" | 写作失败，提交了脚本生成的降级版 | 手动触发重跑；部署了多个平台时，后到的平台会自动校验不通过并重跑 |
| `GATE_SEARCH_MIN` 反复出现 | 模型没有按手册记录搜索，或搜索能力受限 | 检查平台的联网搜索设置；确认手册里的 `tracelog.py search` 被执行 |
| 原文读取大量失败 | 运行环境不允许访问任意网站，或站点拒绝程序访问（403） | 不影响运行：链接仍取自 HN 数据；需要摘要时由搜索补充 |
| 脚本报网络错误、`git push` 连不上 | 运行环境禁止命令联网（Codex 沙箱默认如此） | Codex 云端核对环境网络；CLI/自建沙箱按其权限配置联网 |
| `git` 报只读或 Operation not permitted | 部分沙箱默认保护 `.git` 目录 | 按平台文档放开 `.git` 的写权限；在已隔离的运行环境里，也可以改用 Codex 的 `-s danger-full-access` |
| 脚本报 TLS 或代理错误 | 环境网络策略拦截，或代理证书未配置 | 检查环境网络设置是否放行了这些站点 |
| OSS Insight 请求超时 | 接口偶发挂起 | `rank_github.py` 会重试；仍失败的仓库在数据文件 note 和数据说明中注明 |
| `collect_all.py` 输出 `trendshift_not_ready` | 周榜尚未生成（307、空列表或日期不符） | 手册已安排在其他步骤之后重试；连续出现时考虑推迟运行时间 |
| Trendshift 解析不到 ItemList 或每日数据 | 页面结构变化 | 在数据说明中记录，修订 `collect_trendshift.py` 的解析规则并补测试 |
| `check_run.py` 报"未完成" | 某一步没有在本次运行中做（跳过采集、没重新排名、没记录搜索、没运行 finalize） | 回到那一步补做，不要只改周报文字 |
| `check_portability.py` 报问题 | 执行文件里写进了平台专属的写法或直接的 git 操作，或入口提示词引用了手册步骤编号 | 把平台相关的内容挪到本文第 4 节；git 操作改用 `coord.py` |

| `FEISHU_AMBIGUOUS_DOC` | 同周搜到多篇候选文档，拒绝覆盖 | 人工在飞书保留一篇（删除多余或改标题去掉周编号），再补交付 |
| `FEISHU_SYNC_FAILED` | 覆盖更新重试后仍失败（含 `partial_success` 写入不完整）、缓存文档读取结果不明终止，或上次新建结果不明且搜索 0 候选（tracelog 记 `FEISHU_CREATE_UNKNOWN`） | 先在飞书搜索该周是否已建文档；已建则补交付会覆盖更新，未建则把 `/tmp/ai-weekly/feishu.json` 中该周 `action=unknown` 的记录删除后补交付新建 |
| `FEISHU_SYNC_UNKNOWN` | 新建遇网络失败、结果不明（文档可能已创建） | 同上行：先人工确认该周是否已建文档，再决定补交付或清理记录后重建 |
| `FEISHU_NOTIFY_FAILED` | bot 通知确定拒绝且精简版也失败 | 通知内容已写入平台最后输出；bot 恢复后可手工转发，或重跑 `feishu_sync.py notify` |
| `FEISHU_NOTIFY_UNKNOWN` | bot 通知网络类失败、同一幂等键重试仍不明（首条可能已送达，未换键重发） | 先在飞书查是否已收到该周通知；未收到再重跑 `feishu_sync.py notify` |
| `FEISHU_CLI_NOT_FOUND` / `FEISHU_CONFIG_MISSING` | 运行环境没有 lark-cli 或 `config/feishu.yaml` | 按 4.9 清单安装与配置；飞书交付整体降级，git 发布不受影响 |
