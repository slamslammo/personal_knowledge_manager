# 部署指南

> 本文说明如何验收 AI 资讯任务，并把它部署到定时运行平台。部署所需的全部参数集中在 `config/task.yaml`，本文按平台说明怎么配置。

## 1. 部署前提

任何平台都需要满足：

| 能力 | 用途 |
| --- | --- |
| 定时触发 | 每周一 10:00（Asia/Shanghai）运行 |
| Shell、git | 执行脚本、提交 |
| python3（带 PyYAML） | 运行 `scripts/` 下的采集、排名、校验脚本 |
| 访问外网 | Trendshift、OSS Insight、HN Algolia、Hugging Face，见 `config/task.yaml` 的 `network.allow` |
| 联网搜索 | 官方发布、媒体报道、传播分析 |
| 推送本仓库、合并 PR | 周报和数据文件提交到工作分支，建 PR 并合并到 `main`（Claude 云端用 GitHub MCP 工具） |
| 发送通知 | 把周报精简版推送给用户 |

模型选择平台上的中档通用模型即可。仓库文件中不写具体型号，在平台设置中选择。

## 2. 部署前验收（开发会话）

开发会话是测试环境，定时任务是运行环境。任务工程有改动时，先在开发会话里完整跑一遍，产出确认符合预期后再部署：

1. 在挂载了本仓库的开发会话里运行单元测试：`python3 -m unittest discover -s AI资讯/任务/scripts/tests -t AI资讯/任务/scripts/tests`。
2. 按入口提示词 `prompts/routine-prompt.md` 和执行手册 `prompts/weekly.md` 运行一次，参数加 `TEST_RUN=1`；要测指定的周，再加 `TARGET_WEEK=YYYY-Www`。测试模式不推送 `main`、不发通知，周报和数据文件提交到开发分支，通知内容输出到会话里。
3. 审阅周报、数据文件和通知内容，按反馈调整规则后重跑。
4. 验收通过后合并 PR，再按第 3 节部署或更新定时任务。

## 3. Claude Code 云端定时任务（当前平台）

### 3.1 环境

1. 打开定时任务使用的云端环境，网络访问设为"完全访问"，或者在白名单中加入 `config/task.yaml` 列出的域名。
2. 注意：环境可能被多个会话和定时任务共用，修改会影响所有使用该环境的任务。如需隔离，可单独建一个环境给本任务。
3. 环境中不需要配置额外的密钥或 token。

### 3.2 GitHub 授权

1. **账户级**：在设置的"连接器 → GitHub 集成"中连接 GitHub 账户，并安装 Claude GitHub 应用，确认"查看仓库状态"显示云端会话可以在本仓库中工作。
2. **任务级**：在定时任务的编辑页把本仓库加入仓库列表。云端会话只能推送已挂载的仓库，挂载在会话启动时确定，运行中的会话不会补加。
3. **合并到 `main`**：任务把周报推送到 `claude/` 开头的工作分支，再用 GitHub MCP 工具建 PR 并合并，不需要"允许推送任意分支"。合并失败时会改为直接推送 `main`；两者都失败，周报留在工作分支，通知首句标明"未合并"。

### 3.3 定时任务配置

| 项目 | 设置 |
| --- | --- |
| 运行时间 | 每周一 10:00，时区 GMT+8 |
| 模型 | 中档通用模型 |
| 仓库 | slamslammo/personal_knowledge_manager |
| 提示词 | 复制 `prompts/routine-prompt.md` 全文（入口提示词） |

入口提示词只包含安全规则、失败通知和"按仓库里的执行手册执行"。执行手册、脚本和配置的修改合并到 `main` 后，下一次运行即生效，不需要重新粘贴；只有 `routine-prompt.md` 本身变化时才需要重新粘贴。

### 3.4 上线检查

正式启用前手动触发一次，检查：

- [ ] 周报文件生成在 `AI资讯/周报/{ISO 周年}/{WEEK}.md`，开头有元数据
- [ ] 数据文件生成在 `AI资讯/数据/github-weekly/{WEEK}.json`
- [ ] 有一个标题为"AI 周报 {WEEK}"的 PR，已合并，提交出现在 `main`
- [ ] 手机收到通知，首句格式为"【AI周报 W..】……"，全文链接可以打开
- [ ] 数据说明中各数据源均采集成功；通知的"运行结果"三行显示校验通过、第 0–4 步全部完成、PR 已合并

### 3.5 回溯运行

手动触发定时任务（或新开会话），在提示词前加一行 `TARGET_START=YYYY-MM-DD`（目标周的周一）或 `TARGET_WEEK=YYYY-Www`，即按回溯模式生成该周周报。榜单数据文件已存在时直接复用；不存在且已超出 Trendshift 每日数据的 61 天窗口时，③ 无法精确计算本周增量，要在数据说明中注明。

## 4. 迁移到其他平台

### 4.1 能力对应

| 提示词中的能力 | Claude Code 云端 | 其他平台的对应做法 |
| --- | --- | --- |
| 联网搜索 | 内置搜索工具 | 平台内置搜索，或调用搜索 API |
| 推送通知 | PushNotification（`<routine_summary>` 首句为横幅） | 邮件、飞书或其他 IM 机器人 Webhook、GitHub Issue |
| 推送本仓库 | 挂载仓库后由平台注入凭证 | 部署密钥或细粒度 token，只授予本仓库内容写权限 |

迁移时复制 `prompts/routine-prompt.md`，把其中和 `prompts/weekly.md` 第 6 步里的 PushNotification 与 `<routine_summary>` 替换为目标平台的通知方式，其余步骤不变。

### 4.2 Codex 或本地 cron

1. 准备运行环境：满足第 1 节的前提。脚本只用 Python 标准库和 PyYAML，不依赖 GNU date。
2. 克隆本仓库，配置只对本仓库有写权限的凭证。
3. 按 `config/task.yaml` 的 `schedule` 配置定时。cron 默认使用系统时区，需设置 `CRON_TZ=Asia/Shanghai`，或换算为 UTC 的 `0 2 * * 1`。
4. 用平台的命令行或非交互模式执行入口提示词，并开启联网搜索。
5. 先按第 2 节的测试模式跑一次，再按 3.4 的清单做上线检查。

## 5. 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 推送报 403，提示仓库不在授权列表 | 定时任务没有挂载本仓库 | 在定时任务编辑页挂载仓库 |
| 通知首句标明"未合并" | GitHub MCP 工具不可用、PR 合并被拒，或与 `main` 冲突 | 按通知里的分支名手动合并；检查 Claude GitHub 应用的仓库权限 |
| 通知首句标明"检查未通过" | `check_run.py` 发现有步骤没做完，或 `validate.py` 仍有错误 | 看周报数据说明里的剩余问题；必要时手动触发重跑 |
| api.github.com 返回 403 | 云端会话只允许访问已挂载仓库的接口 | 不要使用 GitHub 搜索和 Trending，改用 Trendshift |
| 脚本报 TLS 或代理错误 | 环境网络策略拦截，或代理证书未配置 | 检查环境网络设置是否为"完全访问"或已加入白名单 |
| OSS Insight 请求超时 | 接口偶发挂起 | `rank_github.py` 会重试；仍失败的仓库在数据文件 note 和数据说明中注明 |
| `collect_trendshift.py` 退出码 3 | 周榜尚未生成（307、空列表或日期不符） | 手册已安排在其他步骤之后重试；连续出现时考虑推迟运行时间 |
| Trendshift 解析不到 ItemList 或每日数据 | 页面结构变化 | 在数据说明中记录，修订 `collect_trendshift.py` 的解析规则并补测试 |
| `validate.py` 报错 | 周报结构、元数据或与数据文件不一致 | 按报错修改；规则本身需要调整时，同步修改模板、`validate.py` 和测试 |
| `check_run.py` 报"未完成" | 某一步没有在本次运行中做（跳过采集、没重新排名、没记录搜索、没重写周报） | 回到那一步补做，不要只改周报文字 |
